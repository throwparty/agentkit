# T-003 — Can one ACP launcher and registry entry serve both runners without changing Tackle?

**Answer: yes. Tackle is already ACP-native, so a wrapper-only launcher plus an
ACP registry entry is enough. No headless mode and no product change are
required. The wrapper must write user config, stage prompts in the project tree,
and leave trust approval to the runner's permission policy.**

## Evidence

### Launch surface

`crates/agentkit-tackle/src/cli/args.rs:26-46`:

```rust
/// Serve ACP over JSON-RPC on stdin/stdout
Stdio {
    /// Override the session database location
    #[arg(long)] db_path: Option<PathBuf>,
    /// Override the user configuration directory
    #[arg(long)] config_dir: Option<PathBuf>,
},
```

There is no headless `run` subcommand. A runner that speaks ACP does not need
one; it spawns `tackle stdio` and drives the session.

### Workspace root

`crates/agentkit-tackle/src/acp/v1/sessions.rs:76-86`:

```rust
pub(super) async fn handle_new_session(..., request: NewSessionRequest, ...) {
    let session = common_session::create_interactive(
        &state, &request.cwd.to_string_lossy(), None,
    )
```

Tackle uses the `session/new` `cwd` as the workspace root, so the runner's task
directory is honoured.

### Client tools (fs + terminal)

`crates/agentkit-tackle/src/acp/v1/client_tools.rs:33-40`:

```rust
impl ClientCaps {
    pub fn from_capabilities(capabilities: &v1::ClientCapabilities) -> Self {
        Self {
            fs_read: capabilities.fs.read_text_file,
            fs_write: capabilities.fs.write_text_file,
            terminal: capabilities.terminal,
        }
    }
}
```

The model sees `client.fs.*` and `client.terminal.*` only when the ACP client
advertises them. Harbor's ACP runner does (PR #1464 restored fs/terminal);
BenchFlow and Evals.si claim ACP clients. A runner without an ACP client cannot
drive Tackle's editor tools.

### Configuration

`crates/agentkit-tackle/src/config/mod.rs:4-8`:

```rust
//! Security-relevant fields — model endpoints and the credential helper —
//! are user-configuration only: a project layer declaring them is rejected
```

`crates/agentkit-tackle/src/config/schema.rs:81-92` defines `EndpointConfig`
(`base_url`, `wire_format`, `auth`, `models`). The only wire format is
`openai-chat-completions`. A launcher must write the endpoint into the
**user** config (`--config-dir`), not the project `.agentkit/tackle/config.toml`.

### Prompts are project definitions

`crates/agentkit-tackle/src/definitions/loaders.rs:92-116`:

```rust
/// Definitions are repository-only: a definition in the user configuration
/// directory would carry resources the model could not reach.
pub fn discover(project_dir: Option<&Path>) -> Result<Definitions, DefinitionError> {
```

Entry points: `prompts/PROMPT.md` for a package, or a flat `<name>.md`
(`loaders.rs:23-28`). Prompt metadata is
`crates/agentkit-tackle/src/definitions/types.rs:160-179`: `description`,
`parameters`, `user_invokable` (default true), `model_invokable` (default false),
`compaction`.

`crates/agentkit-tackle/src/invokables/registry.rs:293-306` registers a
`model_invokable` prompt as an invokable named `prompt.<name>`. So a wrapper
stages the skill/prompt package under
`<workspace>/.agentkit/tackle/prompts/<name>/PROMPT.md` before launching.

### Trust

Project definitions are trust-gated. A non-interactive eval must answer the
trust permission request (or the prompt will not load). That is a runner
permission-policy setting, not a Tackle change.

### Trajectory and usage

`crates/agentkit-tackle/src/acp/v1/sink.rs:66-114` emits:

- `UsageUpdate` with input tokens, context size, and cost in USD when known;
- `ToolCall` with `name`, `kind`, `status`, and `raw_input`;
- `ToolCallUpdate` with status and content.

`crates/agentkit-tackle/src/invokables/titles.rs:33-50`:

```rust
if let Some(rest) = name.strip_prefix("prompt.") {
    return labelled(&format!("prompt {rest}"), arguments);
}
...
pub fn tool_kind(name: &str) -> ToolKind {
    match name {
        "client.fs.read_text_file" => ToolKind::Read,
        "client.fs.write_text_file" => ToolKind::Edit,
        _ if name.starts_with("client.terminal.") => ToolKind::Execute,
        _ => ToolKind::Other,
    }
}
```

A prompt invocation is therefore observable as `name = "prompt.<name>"`, but its
`kind` is `Other`. BenchFlow's `n_skill_invocations` (which counts `kind ==
"skill"`) would not count it; Harbor's trajectory and any custom analysis can
count by name.

### State isolation

`--config-dir` and `--db-path` are per process. The session store is SQLite
(`src/store/sqlite.rs`); the runner does not need it because ACP events carry
the trajectory, but it is available for post-run export.

## Assessment

- **Proven:** ACP stdio launch; `session/new` cwd; client fs/terminal; user-only
  endpoints; project-only prompts; prompt invokable naming; usage/cost; state
  flags.
- **Inferred:** a wrapper can stage a prompt package and auto-approve trust
  without a Tackle change.
- **Unverified:** no runner-specific smoke test yet; no check that every runner
  auto-approves the trust request.

## Minimal launcher contract

1. Read provider/model env from the runner.
2. Write `<config-dir>/config.toml` with `[endpoints.*]`, `[defaults].model`,
   MCP servers, scripts, and permission policy.
3. Copy the prompt/skill package into
   `<workspace>/.agentkit/tackle/prompts/<name>/` (with-prompt arm only).
4. Set a per-run `--config-dir` and `--db-path`.
5. `exec tackle stdio`.
6. Rely on the runner's ACP client for fs/terminal and on its permission policy
   to auto-approve trust.
