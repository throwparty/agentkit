# T-017 — the generic VCS interface, the Git common module, and the arch-lint boundary

**Question:** What is the generic VCS interface, what code is shared between backends, and what arch-lint rules keep the VCS code out of the orchestration code?

**Answer:** Define `vcs` (the trait, `Revision`, `TreeId`, `Capabilities`, `Merge`, `Conflict`, `ConflictSides`) and `vcs::git_common` (Git concepts: ignore matching, archive/tar, object and ref primitives, path safety, naming) first; adapt the existing Git implementation to the trait; add the jj implementation later. `orchestrator` imports only `vcs`; `vcs::git` and `vcs::jj` import `vcs`/`vcs::git_common` but never each other; `vcs::git_common` imports neither. Arch-lint enforces the boundary. The Git common module carries Git concepts that anything using the Git storage backend reuses; it is not VCS-neutral, and the backend-specific code stays in its backend. The target interface must also cover the operations the orchestrator uses today (branch create and delete, branch enumeration, archive materialisation, snapshot commit and filter, remote/direct fact), or removing `Scm` loses behaviour.

## Interface

```rust
pub struct Revision(String); // opaque
pub struct TreeId(String);   // opaque

pub struct Capabilities {
    pub conflict_model: ConflictModel, // Native | Blocking
    pub op_log: bool,
    pub bindings: BindingSupport,      // Copied | Bound | both
    pub export: ExportSupport,         // jj Git export, or none
}

pub trait Vcs {
    fn capabilities(&self) -> Capabilities;

    fn prepare(&self, sandbox: &str) -> Result<Workspace, Error>;
    fn masked_paths(&self, workspace: &Workspace) -> Vec<PathBuf>;

    fn identity(&self, workspace: &Workspace) -> Result<TreeId, Error>;
    fn materialise(&self, workspace: &Workspace, rev: &Revision) -> Result<(), Error>;
    fn snapshot(&self, workspace: &Workspace, message: &str, parents: &[Revision]) -> Result<Revision, Error>;

    fn tip(&self, branch: &str) -> Result<Revision, Error>;
    fn set_tip(&self, branch: &str, rev: &Revision) -> Result<(), Error>;
    fn synced(&self, branch: &str) -> Result<Revision, Error>;
    fn set_synced(&self, branch: &str, rev: &Revision) -> Result<(), Error>;

    fn merge(&self, base: &Revision, ours: &Revision, theirs: &Revision) -> Result<Merge, Error>;
    fn conflicts(&self, rev: &Revision) -> Result<Vec<Conflict>, Error>;
    fn conflict_sides(&self, rev: &Revision, path: &Path) -> Result<ConflictSides, Error>;
    fn resolve(&self, rev: &Revision, paths: &[PathBuf]) -> Result<Revision, Error>;
    fn abort(&self, rev: &Revision) -> Result<(), Error>;

    fn history(&self, branch: &str, keep: &HistoryPolicy) -> Result<Vec<Revision>, Error>;
    fn restore(&self, branch: &str, rev: &Revision, mode: RestoreMode) -> Result<(), Error>;
    fn export(&self) -> Result<(), Error>; // jj: jj git export; Git: no-op
}
```

`Merge` is `Clean { revision }` or `Blocked { conflicts }`; `Native` returns a conflicted revision, `Blocking` returns `Blocked` and the workspace markers. `HistoryPolicy` and `RestoreMode` come from the user configuration (T-015), with no default.

The list above is the target surface, not yet the whole first cut. The orchestrator today also deletes branches (`Scm::delete_branch`), enumerates sandbox branches (`list_sandboxes`), builds the snapshot filter (`snapshot_filter`) and reads the remote/direct fact (`mode`). `prepare` may cover creation; the rest need a home, whether as trait methods, `Workspace` accessors or composition-point construction. `Scm::apply_patch` and `Scm::repo_prefix` are declared but have no caller outside `scm`; they can be dropped. The plan decides which cut ships first; no operation may remain a direct `scm`/`vcs_store` call in the orchestrator. The signatures above are illustrative; the ADR plan settles them and adds the operations orchestration performs today (`snapshot_filter`, `sandboxes`, `delete_branch`, `state_path`, `expose` and `prune`).

All signature types — `BranchName`, `Revision`, `TreeId`, `Workspace`, `Prepared`, `Capabilities`, `Merge`, `Conflict`, `ConflictSides`, `HistoryPolicy`, `RestoreMode` — are owned by `vcs`; `vcs::git_common` owns algorithms only, so the orchestrator never imports it. Binding is not a call argument: it is a property of the configured backend (T-010), reported through `Capabilities` and stored in the record. `WorkspaceBinding` is therefore a type `vcs` exposes, not a parameter `prepare` takes.

## Git common module

`vcs::git_common` holds the Git concepts anything using the Git storage backend reuses:

- ignore matching (`.gitignore` semantics, the snapshot filter);
- archive building, `git2::Tree` walking, and tar unpacking with the path confinement it enforces;
- Git object and ref primitives;
- branch/sandbox naming;
- `GitError`, the old `ScmError`.

Not shared: `Revision`/`TreeId`/`Capabilities`/`Merge`/`Conflict`/`ConflictSides` (owned by `vcs`), Git refs/reflogs/merge-tree orchestration, jj bookmarks/workspaces/op log/conflict algebra/export. Those live in the contract or the backend. `git_common` is Git-specific: a non-Git-backed VCS would not use it, and workspace binding/masking is not a Git concept, so a backend that binds implements it in its own module.

## Arch-lint boundary

- `orchestrator` may import `vcs` but not `vcs::git`, `vcs::jj` or `vcs::git_common`.
- `vcs::git` may not import `vcs::jj`; `vcs::jj` may not import `vcs::git`.
- `vcs::git` and `vcs::jj` may import `vcs` and `vcs::git_common`; `vcs::git_common` may import neither backend.
- `cli`/`mcp` reach VCS only through the orchestrator; `sandbox`/`backends` do not import `vcs`.
- A composition root is the only place that constructs `GitVcs`/`JjVcs`. Today construction is split: `Sandboxes::open` (`orchestrator/service.rs:65`) is the entry point both surfaces use, but `open_scm` (`:1264`) chooses the mode inside the orchestrator. One of the two becomes the construction point.

How the rules are expressed, verified against the pinned tool (arch-lint 0.11.0, `nix/flake.nix:79-98`):

- `[[scopes]]` match `paths` globs and support `exclude`. `litterbox-vcs` uses `exclude` to stay disjoint from `src/vcs/git_common/**`, `src/vcs/git/**` and `src/vcs/jj/**`.
- `[[deny-scope-dep]]` takes one `from` and a list of `to` scopes and checks both `use` imports and inline qualified paths by default (`check-inline = true`), so `crate::vcs::git::GitVcs::new()` is caught without a `use`.
- `[[independent]]` over the two backend scopes expresses "these must not depend on each other"; it needs at least two scopes, so it lands with `vcs::jj`.
- `hack/arch-lint-negative.sh` is the existing proof pattern: it plants an import, requires `arch-lint check` to fail with the named rule, and restores the file on every exit path (`trap ... EXIT INT TERM`). `just lint` runs `arch-lint check` and the fixture.

## Order

1. Define `vcs` and `vcs::git_common`; add the arch-lint rules.
2. Adapt the existing Git implementation to the interface; keep behaviour.
3. Build the plan/conflict surface on the interface with Git `Blocking`.
4. Add the jj implementation later; it uses `vcs::git_common`, never `vcs::git`.
