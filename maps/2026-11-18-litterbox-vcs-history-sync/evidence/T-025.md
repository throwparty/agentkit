# T-025 — sandbox history and restore without a common retention policy

**Question:** How should `litterbox history` and `litterbox restore` work now that Git and jj cannot share a retention policy?

**Answer:** A history step is a commit the shared branch pointed at. `history` lists what the clone's log still has. For Git that is the reflog of `refs/heads/litterbox/<name>`. For jj that is the clone's operation log, filtered to the bookmark `litterbox/<name>`; no operation from another sandbox is a step. The sandbox branch's commits that never reached the shared branch are current sandbox state, not history steps.

`restore` never rewrites. It creates one new commit on the shared branch whose tree is the selected commit's tree and whose parent is the current shared branch commit. It then moves the shared branch, the sandbox branch and `synced` to the new commit. The old tip stays in the log. Under `remote` the commit is written in Litterbox's clone; under `direct` it is written in the user's clone. The user's checkout is never written.

There is no `[history]` section, no count and no age. Git and jj count and prune different things, so a common policy would be a fiction. Pruning is an optional `config` string in `[vcs.git]` or `[vcs.jj]`, applied to Litterbox's clone. Git accepts Git config syntax. jj accepts TOML. The backend replaces its overlay rather than appending. Under Git `direct` the key is refused because Litterbox has no clone.

`restore` refuses when it would lose work. A `diverged` sandbox, unsaved workspace changes or a staging workspace require `--discard-work`. An open resolution requires `--discard-resolution`. A Git tip commit whose tree contains marker text is allowed with `--discard-work`, because the new tree is clean. A conflicted jj commit is refused even with the flag, because a child of a conflicted jj commit is still conflicted.

The commands are operator-only. There is no MCP tool. The ADR is `adrs/2026-11-24-keep-and-restore-sandbox-history`.
