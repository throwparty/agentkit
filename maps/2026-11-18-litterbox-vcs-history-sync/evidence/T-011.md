# T-011 — operator CLI surface

**Question:** What is the operator CLI surface, and how does it share the `plan` logic with MCP?

**Answer:** The CLI is the operator's surface for the same state the agent sees over MCP. The commands are `status`, `conflicts`, `resolve`, `abort`, `shell` and an optional `sync`; every one calls the orchestrator's `plan` and returns the same `workspace` object as the MCP tools. The CLI does not implement a second state machine.

## Commands

| Command | Meaning |
|---|---|
| `litterbox status <name> [--json]` | Full source state: axes, `branch_tip`, `synced`, workspace tree, merge state, conflicts, VCS, binding, `resolution`, `notice`. |
| `litterbox conflicts <name> [--json] [--sides <path>]` | Conflict paths and kinds; `--sides` adds the base/ours/theirs view for one path. |
| `litterbox resolve <name> [paths...] [--all]` | Mark the edited paths resolved; commit the merge/resolution; return the new state. |
| `litterbox abort <name>` | Discard the pending merge and restore the pre-merge workspace. |
| `litterbox shell <name> [-- command...]` | Enter the sandbox to edit or test; existing command. |
| `litterbox remote <name>` | Existing Git remote install; Git-backed sandboxes only. |

- `resolve` and `abort` are top-level, matching `pause`, `resume`, `delete`, `shell`.
- `status` is the operator's read view; `list` remains the inventory and may gain a one-line source summary.
- `--json` mirrors the MCP `workspace` block so scripts and operators see the same fields.
- Exit classes are the existing taxonomy: a blocking conflict is `conflict` (exit 4), an unsupported backend/VCS/binding is `unsupported` (exit 5), and a failed merge is `failed` (exit 1).

## Sharing `plan`

- `status` calls `classify` and returns the axes and the merge record.
- `conflicts` calls the VCS's `conflicts`/`conflict_sides` operations.
- `resolve`/`abort` call `plan(state, Resolve|Abort, model)` and execute the returned steps.
- There is no separate `sync` command: reconciliation is lazy, at the start of the next operation that touches the workspace. `status` reports; the next `shell`/tool call reconciles.
- MCP calls the same orchestrator methods; the CLI has no separate rules.

## Operator workflow

1. The operator rewrites the branch in their working copy and pushes it to the bridge (Git or jj).
2. `litterbox status <name>` shows `ContentMoved` or `Diverged` and, after the next operation, `Conflicted`.
3. `litterbox shell <name>` opens the sandbox; the operator edits the markers, or uses `litterbox conflicts --sides` to inspect the sides.
4. `litterbox resolve <name> --all` commits the resolution; `litterbox abort <name>` discards it.
5. The next sandbox operation reconciles the branch; there is no `sync` command. If the operator wants to force the state, running a command through `shell` is the trigger.

## Open taste questions

1. Should there be a forced-reconcile command (`sync` or `reconcile`)? The recommendation is no for now; lazy reconciliation covers the normal workflow. If operators ask for it, it is a thin wrapper over `plan`.
2. Should `resolve` launch a merge tool? No; the operator edits in the workspace or via `shell`. A merge tool would be a second conflict interface.
3. Should `status` be an alias of `list --json` for one sandbox? `list` is an inventory; `status` is a single sandbox's source state. The recommendation is a separate command.
