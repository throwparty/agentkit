# T-024: which jj workflow do agents understand

**Question.** Which jj workflow do agents understand: resolving at the commit that introduced the
conflict, or resolving in a child and squashing it into that commit?

## Method

Two identical fixtures, built by `evidence/T-024/fixture.sh`. Each has a base commit, a user commit
and a sandbox commit that both rewrite line 1 and line 20 of `file.txt`, and a user-authored merge
commit that was committed without resolving and pushed to `litterbox/probe`. The working copy sits on
the conflicted tip, as a user's checkout would.

Every subagent role available here runs with `bash: deny`, so neither agent could execute anything.
The experiment ran by proxy. Each agent proposed one command, the operator ran it and returned the
output verbatim, and the loop repeated. That is slower than a shell, and it puts every command on the
record.

Run A used the `in-place` fixture and the instruction "resolve the conflict by fixing it in the
commit that introduced it". Run B used the `on-top` fixture and "resolve the conflict and make sure
the fix ends up in the commit that introduced it, not in a new commit stacked on top of it". Neither
was told any `jj` command.

## Run B, on-top framing: pass after a correction

1. Read the state and concluded that the conflicted merge commit is `@`, so editing the working copy
   rewrites the commit that introduced the conflict and needs no new commit. It resolved in place.
2. Rebuilt `file.txt` from a heredoc, working from a dump that the operator had truncated. The
   rewrite dropped filler lines 22 to 24.
3. When told, named the three checks that would have caught it: `jj diff` before `jj status`, a line
   count against the original, and refusing to reconstruct a region the dump had elided.
4. Restored the three lines and verified.

Final state, checked independently of the agent: the bookmark and the working copy are at `18aa6a63`,
the sandbox commit `ad8137c5` is unchanged, `jj resolve --list` exits 2, and the diff from base shows
the two sides' additions and nothing else.

## Run A, in-place framing: fails twice, both times silently

1. First command was `python3`, absent on this host.
2. Fell back to `sed -i '/^[<+>%\\-]/d' file.txt`, which deletes every line that begins with a marker
   character. jj marks an addition from the side it is not diffing with a leading `+`, so this
   deleted the user's contribution in both regions:

   ```
   $ jj resolve --list -r litterbox/probe
   Error: No conflicts found at this revision      exit: 2
   $ head -1 file.txt
   // sandbox: make the client retry with backoff
   ```

3. Diagnosed its own error in prose, then proposed an `awk` that strips `+` prefixes from a file the
   `sed` had already stripped. It changed nothing: 24 lines, zero user lines, no conflicts reported.
4. Could not recover by editing, because the conflicted content was gone from the working copy. It
   reached for `jj op restore`. Told that the clone is shared and a repository-wide restore would
   rewind other sandboxes, it chose the correct recovery without prompting: rebuild the merge from
   its two untouched parents with `jj new <user> <sandbox>`. That reproduced the conflict and needed
   no saved state.
5. Re-ran the corrected `awk` on the fresh conflict. It stripped one `+` from jj's `+++++++` section
   header and printed the rest, so commit ids became file content:

   ```
   $ jj resolve --list -r @
   Error: No conflicts found at this revision      exit: 2
   $ head -3 file.txt
   // user: fold the retry helper into the client
   ++++++ znuszorl 3d0eae14 "sandbox: make the client retry with backoff"
   // sandbox: make the client retry with backoff
   ```

   The marker scan returns zero here, because the markers were rewritten into garbage. Its own two
   diffs against the sides were what exposed it.
6. Asked how it would avoid editing markers by character, it named the right shape: merge the three
   versions instead of parsing markers, with `git merge-file --union` over `jj file show -r
   <base|ours|theirs>`. `jj resolve --tool=:union` does not work out of the box, because it needs
   `merge-tools.:union.merge-args` in config.

## Three-way merge over the sides

`evidence/T-024/merge-file/` holds the experiment. With the three versions written out:

```
$ git merge-file --union merged.txt base.txt theirs.txt
exit: 0
markers: 0
26 lines, both sides' additions present, nothing else moved
```

## What this establishes

- The two workflows did not separate the agents. Both chose to resolve in place, and neither added a
  child commit when told not to. The framing changed nothing about the procedure. Verification
  discipline is what separated them.
- "The VCS reports no conflicts" is necessary and not sufficient. Run A produced two trees that
  passed every check Litterbox can run, the conflict query, the marker scan, bookmark consistency and
  ancestry, while one held none of the user's work and the other held conflict-header garbage. Only a
  diff against each side caught either.
- Editing markers by character is not a resolution procedure. It failed twice, in two different
  ways, and each failure was invisible to the conflict query. A three-way merge of the three versions
  is the reliable shape, and it needs the three versions.
- Recovery must be scoped. Once a wrong resolution replaces the tree, the conflicted content is gone.
  The agent's first instinct, `jj op restore`, is repository-wide and would rewind every other
  sandbox in the shared clone. The correct recovery rebuilds the merge from its recorded parents,
  which is `stage` run again and needs no new VCS operation.
- jj's marker format is not Git's. jj writes `<<<<<<< conflict 1 of 2`, `%%%%%%% diff from:`,
  `\\\\\\\ to:` and `+++++++`. Any helper that strips markers by character would be wrong for one
  backend.

## Answer

Agents understand resolution at the commit that introduced the conflict when the working copy already
holds it, and they do not add a child commit unless told to. Resolving in place is the workflow to
drive. Resolving in a child and squashing adds work without adding capability.

What agents do not do is prove that the result kept both sides, and they cannot undo a wrong one
without reaching for a repository-wide restore. Three things follow. The three sides of each
conflicted path should be readable as files. The check for resolution should compare the result with
each side. Abandon should re-materialise the merge from its recorded parents.
