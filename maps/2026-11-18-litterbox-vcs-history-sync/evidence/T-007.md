# T-007 — `plan`/`decide` for each action and conflict model

**Question:** What is the exact `plan`/`decide` sequence for each action (tool, snapshot, rewrite, merge, resolve, abort, repair) and each conflict model?

**Answer:** The state is derived from three axes; `plan` is the only consumer and returns an ordered `Vec<Step>`. A tool call runs `plan` before the tool (adopt, merge, or block), runs the tool, then runs `plan` again to snapshot or merge; the result is the post-plan state and is what every MCP `workspace` block reports. `Blocking` is Git's pending-merge model; `Native` is jj's. `Deferred` is rejected (T-014).

## Axes and classification

```rust
enum Base { Synced, HistoryMoved, ContentMoved }
enum Workspace { Clean, Dirty }
enum Merge { None, Pending, Conflicted }

struct SourceState { base: Base, workspace: Workspace, merge: Merge }

fn classify(synced: Oid, branch: Oid, workspace_tree: TreeId) -> SourceState {
    let synced_tree = tree_of(synced);
    let branch_tree = tree_of(branch);
    let base = if branch == synced { Synced }
        else if branch_tree == synced_tree { HistoryMoved }
        else { ContentMoved };
    let workspace = if workspace_tree == synced_tree { Clean } else { Dirty };
    // merge comes from the record (`Pending` while markers are materialised)
    SourceState { base, workspace, merge }
}
```

## `plan`

```rust
enum Step {
    Proceed, AdoptHistory, AdoptContent, Merge, Snapshot,
    Block(BlockReason), Resolve, Abort, Materialise,
}

fn plan(s: SourceState, a: Action, m: ConflictModel) -> Vec<Step> {
    use Base::*; use Workspace::*; use Merge::*;
    match (s.base, s.workspace, s.merge) {
        (Synced, Clean, None) => vec![Step::Proceed],
        (Synced, Dirty, None) => vec![Step::Snapshot],
        (HistoryMoved, Clean, None) => vec![Step::AdoptHistory],
        (HistoryMoved, Dirty, None) => vec![Step::AdoptHistory, Step::Snapshot],
        (ContentMoved, Clean, None) => vec![Step::AdoptContent],
        (ContentMoved, Dirty, None) => vec![Step::Merge],
        (_, _, Pending) => vec![Step::Merge],
        (_, _, Conflicted) => match (a, m) {
            (Action::Resolve, _) => vec![Step::Resolve],
            (Action::Abort, _) => vec![Step::Abort],
            // The agent must be able to edit and test to resolve.
            (Action::Tool, _) => vec![Step::Proceed],
            (Action::Snapshot, ConflictModel::Native) => vec![Step::Snapshot],
            (Action::Snapshot, ConflictModel::Blocking) => {
                vec![Step::Block(BlockReason::Conflict)]
            }
            (Action::Repair, _) => vec![Step::Materialise],
            _ => vec![Step::Proceed],
        },
        (_, _, _) if a == Action::Repair => vec![Step::Materialise],
        _ => vec![Step::Proceed],
    }
}
```

## Action sequences

### Tool call (`bash`, `read`, `write`, `patch`, `ls`, `glob`, `grep`)

1. `plan(state, Tool)`:
   - `HistoryMoved` → `AdoptHistory` (advance `synced`).
   - `ContentMoved`/`Clean` → `AdoptContent` (update the workspace).
   - `ContentMoved`/`Dirty` → `Merge` (materialise; may become `Pending`/`Conflicted`).
   - `Conflicted`/`Blocking` → `Proceed` (the agent can edit/test).
   - `Conflicted`/`Native` → `Proceed`.
2. Run the tool.
3. `plan(state', Snapshot)`:
   - `Dirty` → `Snapshot`.
   - `Conflicted`/`Native` → `Snapshot` (jj snapshots the working-copy commit; the conflict may persist or clear; `jj resolve --list` is the check).
   - `Conflicted`/`Blocking` → `Block` (the branch does not advance; the workspace edits remain).
4. Return the post-plan `workspace` block. For `write`/`patch`, `applied: true` if the edit landed even when the snapshot is blocked. For `bash`, `ran: true|false`; if it did not run, the reason.

### Snapshot (after every mutating tool)

- `Dirty` → build the tree, commit on the branch, set `synced = branch`, state `InSync`.
- `HistoryMoved`/`Dirty` → commit on the moved tip (no merge), set `synced`.
- `ContentMoved`/`Dirty` → `Merge`.
- `Conflicted`/`Native` → commit the working-copy commit; the conflict remains if `jj resolve --list` is non-empty.
- `Conflicted`/`Blocking` → `Block`; the branch stays at the user tip; the workspace keeps the markers.

### User rewrite

There is no direct action. The next operation calls `classify` and sees `HistoryMoved` or `ContentMoved`; `AdoptHistory`/`AdoptContent`/`Merge` handles it. A pure rewrite with an equal tree only advances `synced`; it does not touch the workspace.

### Merge

- **`Blocking`**: run `git merge-tree --write-tree --merge-base=<synced_tree> <branch> <sandbox_side>` (T-004). On clean, write the tree to the workspace, commit the merge, set `synced`, `InSync`. On conflict, write the marker tree to the workspace, record `merge: Pending` with `base/ours/theirs`, leave the branch at the user tip, state `Conflicted`; no descendants.
- **`Native`**: `jj new <ours> <theirs>` (or the equivalent rebase) creates the conflict commit; move the `litterbox/<name>` bookmark; the workspace materialises jj markers; state `Conflicted`; descendants are allowed.

### Resolve

- **`Blocking`**: the agent edits the workspace; `sandbox-resolve` checks that no conflict markers remain, builds the resolved tree, commits a merge with parents `[branch, sandbox_side]`, moves the branch, sets `synced`, clears `Pending`, `InSync`.
- **`Native`**: the agent edits the workspace; `jj status`/any jj command snapshots the working-copy commit; `sandbox-resolve` verifies `jj resolve --list` is empty, moves the bookmark, sets `synced`, `InSync`. If the conflict is a parent, `jj squash`/`jj amend` moves the resolution into it (T-003).

### Abort

- **`Blocking`**: discard `Pending`; restore the workspace to the pre-merge tree (stored in the record); state `Diverged` (or `ContentMoved` if the sandbox had no changes).
- **`Native`**: `jj op restore` to the operation before the merge, or `jj abandon` the conflicted commit; restore the bookmark/workspace; state `Diverged`.

### Repair (missing compute)

- `Materialise` from the branch (or the surviving workspace). `InSync`; for `Native`, a conflicted branch materialises with markers and stays `Conflicted`. `Blocking` durability is T-009.

## MCP result

Every sandbox tool returns:

```json
{
  "workspace": {
    "state": "conflicted",
    "resolution": "required",
    "branch_tip": "5d6e7f8",
    "synced": "1a2b3c4",
    "conflicts": [{"path": "src/a.rs", "kind": "content"}],
    "notice": "the branch moved; merging produced 1 conflict; the next snapshot is blocked",
    "next": "edit src/a.rs and call sandbox-resolve, or call sandbox-resolve with action=abort"
  }
}
```

- `resolution` is `required` for `Blocking`, `deferred` for `Native` (the agent can continue; the conflict persists).
- `read`/`ls`/`grep` carry the same block so the agent has context without asking.
- `sandbox-status` is the full refresh; `sandbox-conflict` returns the sides for one path; `sandbox-resolve` resolves or aborts.

## No tool blocking

No sandbox tool is blocked while conflicted. `read`, `write`, `patch`, `bash`, `ls`, `glob` and `grep` all run. For `Blocking`, only the post-tool snapshot is held, because Git cannot commit a conflicted tree; the workspace edits remain and the branch does not advance. For `Native`, the snapshot runs and the conflict persists or clears according to `jj resolve --list`. The distinction is the branch, not the agent.

`sandbox-resolve` verifies the conflict state (markers for Git, `jj resolve --list` for jj) and accepts optional `paths` to scope the check; it does not require a separate edit tool.
