# T-018 — denying a masked path inside an allowed Seatbelt workspace

**Question:** Can Seatbelt deny a path inside a workspace it already allows, so a bound workspace can hide `.git` or `.jj`?

**Answer:** Yes. SBPL resolves rules last-match-wins, so a `(deny file-read* (subpath <ws>/.jj))` and a `(deny file-write* (subpath <ws>/.jj))` emitted *after* the workspace allow rules override them. The `.jj` entry stays visible in a parent listing, but every open, read, write and stat under it returns `EPERM`, and descendant processes inherit the denial. This is "deny-access" masking: the entry is present but inaccessible, which is distinct from bubblewrap/Docker's empty-mountpoint masking.

## Reproduction

`probe.sh` builds a profile that mirrors the production renderer (`backends/seatbelt/policy.rs` plus the `defaults.rs` baseline table) and appends the proposed deny layer, then runs it under `sandbox-exec` (the documented fallback). The production primitive, `sandbox_init_with_parameters`, is `PRESENT` on this host (via `RTLD_DEFAULT`; it lives in `libSystem.B.dylib` — `libsystem_sandbox.dylib` is gone), and compiles the same SBPL, so the deny-rule ordering carries over. Run:

```sh
bash maps/2026-11-18-litterbox-vcs-history-sync/evidence/T-018/probe.sh
```

## Key observations

- Reading a normal workspace file succeeds; writing one succeeds.
- Reading or writing under `<ws>/.jj` fails with `Operation not permitted` (`EPERM`); the write never reaches the host (`evil.txt` is not created).
- `ls <ws>` lists the other entries but reports `.jj` as `Operation not permitted` — the entry is visible but not stattable.
- `ls <ws>/.jj` and `stat <ws>/.jj` both fail, so `(subpath …)` covers the directory itself, not only its descendants.
- A descendant process is denied the same way.

## Implication

Seatbelt can mask a bound workspace by deny rule, so `Bound` is reachable on macOS. The renderer must emit the deny rules *after* the allow rules — ordering is load-bearing. The observable differs from bubblewrap/Docker: the entry is present-but-inaccessible rather than an empty mountpoint, and the backend documentation should state this per backend.
