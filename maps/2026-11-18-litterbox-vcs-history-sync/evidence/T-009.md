# T-009 — lifecycle interaction with the source state

**Question:** How do pause, missing, repair and delete interact with the source state, especially a conflicted sandbox?

**Answer:** Lifecycle and source are orthogonal. Pause and resume do not touch the source. Missing compute preserves the source; repair materialises the branch (or the surviving workspace) and restores the axes. For `Native`, the conflict is in the commit and survives repair; for `Blocking`, the pending merge is **not** in the branch, so the record must persist `base`/`ours`/`theirs` and the pre-merge workspace tree to re-materialise it. Delete removes the branch, the `synced`/`workspaces`/`previous` refs, the workspace and the merge record; a conflicted sandbox warns and requires `--force` because the branch may contain markers and unresolved work.

## Pause and resume

- No source change. A conflicted sandbox stays conflicted; a paused sandbox accepts no commands, so the agent cannot resolve until resume.
- `pause`/`resume` are lifecycle operations; they do not call `plan`.

## Missing and repair

| Source state | Repair behaviour |
|---|---|
| `InSync` | Materialise from the branch; `synced = branch`; `InSync`. |
| `SandboxDirty` | If the workspace survives, reuse it; if not, the un-snapshotted changes are lost and the branch is the durable half. Materialise from the branch; `InSync`. |
| `HistoryMoved`/`ContentMoved` | Materialise from the branch; `synced = branch`; adopt/merge as needed on the next operation. |
| `Diverged` | Materialise the sandbox side from the workspace or the branch; merge on the next operation. |
| `Conflicted` / `Native` | The conflict is in the commit; materialise the branch with markers; `jj resolve --list` shows the paths; `Conflicted` persists. |
| `Conflicted` / `Blocking` | The pending merge is not durable in the branch. The record persists `base`/`ours`/`theirs` and the pre-merge workspace tree. If the workspace survives, keep the markers; if it does not, write the marker tree from the persisted sides; `Pending` persists. If the sides are gone, drop the pending merge and reconcile from the branch, which may recreate the conflict; never silently resolve. |

`Blocking` durability is a design risk: the only durable copy of the sandbox side is the workspace (or the last snapshot commit), and the merge sides are in the record. Repair must not resolve or discard a conflict silently. The record fields are small (three OIDs/tree IDs plus the pre-merge tree ID).

## Delete

- `--force` means “stop it even if it is running”; it is not a conflict confirmation. A conflicted sandbox is not special for force.
- Before removal, warn about work that the branch holds and that is not merged: commits or changes since the recorded base (or the user's current HEAD, when the host repo can answer). Name the branch tip and the count; do not require a separate confirmation for the conflict itself.
- Remove the branch/bookmark, `refs/litterbox/synced/<name>`, `refs/litterbox/workspaces/<name>`, the merge record and the workspace. A history ref/reflog, if kept, is T-015.
- For `Native`, `jj op log` may retain the commits until GC; do not promise recovery after delete. A global `jj op restore` is not an abort mechanism on the shared bridge (see below).
- A deleted sandbox is not recoverable from Litterbox; the user's own working copy and remotes are the recovery path.

## Abort on a shared jj bridge

`jj op log` is per repository, and the bridge is shared by every sandbox. A global `jj op restore` would undo another sandbox's operations. Abort a `Native` merge by abandoning the sandbox's conflict commit and moving the sandbox bookmark back (`jj abandon`, `jj bookmark set`), not by restoring the repository operation. The user's own repo keeps the op log that protects their changes.

## Open taste questions

1. How much history should a Git bridge keep? T-015 is open; the candidate is a reflog on the `synced` ref in the bridge, not a stack of `previous` refs in the user's repository.
2. Should repair keep a conflicted `Blocking` merge or drop it? The recommendation is keep it if the sides are in the record; drop only when the sides are gone, and say so.
3. The unmerged warning compares against the recorded base and says "since the sandbox was created". If the host repository can cheaply answer, it may add the current HEAD, but the warning never depends on the host being reachable.
