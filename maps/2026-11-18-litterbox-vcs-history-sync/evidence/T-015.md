# T-015 — multiple steps of sandbox history without cluttering the user's repository

**Question:** How should Litterbox keep multiple steps of sandbox history without putting bookkeeping refs in the user's repository?

**Answer:** The retention and restore semantics are **configuration with no default**. Litterbox does not choose a count, a time window, or rewrite-versus-revert on the user's behalf. The configuration lives in the machine-owned user configuration, beside `[workspace] binding`, and is required when history is used. If `[history]` is absent, `litterbox history` and `litterbox restore` report that history is not configured; there is no silent fallback.

## Proposed configuration

```toml
[history]
# Required when history/restore are used. No default.
keep = ...        # the user's retention choice: count, window, or both
restore = ...     # the user's restore choice: rewrite the sandbox branch, or a forward revert commit
```

The exact value grammar is for the ADR; the map records only the choice that the policy is user configuration with no default.

## Mechanism

- **Git:** one `refs/litterbox/synced/<name>` ref in the bridge, with `core.logAllRefUpdates=always`, so every move is a reflog entry. `litterbox history <name>` reads the reflog; `litterbox restore <name> <n>` moves the `synced` ref, the workspace and the branch to that entry and reconciles. No stack of refs; the bridge is a separate bare clone, so the user's repository only sees the branch. Retention is applied to the reflog according to the configured `keep`.
- **jj:** the native op log; `history` filters it to the sandbox's bookmark, `restore` uses `jj bookmark set`/`jj abandon` scoped to the sandbox, never a global `jj op restore`. Retention is applied to the bridge's operation log according to the configured `keep`.

The user's own repository is not the history store. The bridge is; the user sees the branch.
