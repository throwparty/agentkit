# T-008 — how the refs are represented in Git and jj

**Question:** How are the `workspaces`, `synced` and `conflicts` refs represented in jj and Git, and who updates them?

**Answer:** The branch and the merge base are the only concepts both VCS share. Git keeps them as refs; jj keeps the branch as a bookmark and the merge base as a bookmark/record field. The `workspaces` ref exists only in Git (the working-copy-as-a-commit); jj has a working-copy commit per workspace. `Blocking` has no conflict ref: the pending merge is a record plus workspace markers. `Deferred` was rejected, so there are no conflict notes/refs in the design.

## Git

| Ref | Meaning | Writer |
|---|---|---|
| `refs/heads/litterbox/<name>` | the shared branch (durable history) | `GitVcs::snapshot` / `set_tip` |
| `refs/litterbox/workspaces/<name>` | the sandbox snapshot commit (working-copy-as-a-commit) | `GitVcs::snapshot` |
| `refs/litterbox/synced/<name>` | the branch tip the sandbox last agreed on; the merge base | `GitVcs::set_synced` after snapshot/adopt/resolve |
| `refs/litterbox/synced/<name>` reflog | the multi-step history, when `core.logAllRefUpdates=always` is set on the bridge | `GitVcs` (the ref move writes it) |
| — | `Blocking` merge state: `base`, `ours`, `theirs` OIDs/tree IDs plus the pre-merge workspace tree | the sandbox record (`Pending`) |

- The user-facing fetch refspec remains `+refs/heads/litterbox/*:refs/remotes/litterbox/*`; `refs/litterbox/*` is bookkeeping, hidden from the normal fetch but inspectable with `git for-each-ref` or `litterbox status --json`.
- No `refs/notes/*` and no `refs/litterbox/conflicts/*`: notes are not part of the design (T-005/T-014).
- **History is T-015, open.** The current candidate is one `synced` ref with `core.logAllRefUpdates=always` on the bridge, so every move is a reflog entry; `litterbox history` reads it and `litterbox restore` moves the ref and reconciles. That keeps multiple steps back without a stack of refs, and the bridge is a separate bare clone, so the user's repository is not cluttered. A bounded `refs/litterbox/history/<name>/<n>` stack is the alternative; `previous` in the user's repository is rejected.

## jj

| Concept | Meaning | Writer |
|---|---|---|
| bookmark `litterbox/<name>` | the shared branch | `JjVcs` via `jj bookmark set` |
| bookmark or record field `litterbox/synced/<name>` | the branch tip the sandbox last agreed on; the merge base | `JjVcs` after snapshot/adopt/resolve |
| jj workspace | the sandbox workspace (one per sandbox) | `JjVcs::prepare` via `jj workspace add` |
| working-copy commit | the snapshot; jj maintains it | `JjVcs` / jj |
| conflict | in the commit's tree list; `jj resolve --list` | jj |
| `jj op log` | the recovery journal; `jj op restore` / `jj undo` | jj |

- `jj git export` writes bookmarks to the bare Git store as `refs/heads/litterbox/<name>`; T-001 proved the bookmark must exist and export must run for the Git view to move.
- The bridge's initial `default` workspace is unused; the sandboxes are additional workspaces.
- There is no `workspaces` ref: the workspace has its own `.jj` and working-copy commit; the bridge is the shared repo.
- `previous` is not a ref: the jj op log is the backup. Litterbox records the pre-operation commit in the sandbox record for diagnostics.

## Who updates

The VCS backend owns every write. The orchestrator calls semantic operations (`snapshot`, `set_tip`, `set_synced`, `adopt`, `merge`, `resolve`, `abort`); it never writes a ref itself. The backend decides whether that is a Git ref update, a jj bookmark plus `jj git export`, or a jj operation. This is the T-025 contract.

## Open taste questions

1. Should `refs/litterbox/*` be visible in `git for-each-ref`? It will be, because it is a normal ref namespace. The user-facing fetch refspec excludes it; `litterbox status --json` exposes the same facts. The alternative is a separate hidden store under the data directory, which is less inspectable.
2. Should `previous` be one ref per sandbox (overwritten) or timestamped? One is simplest; timestamped is more recoverable but grows the ref namespace.
3. Should `synced` be a ref in Git and a bookmark in jj, or a record field in both? A ref is inspectable and survives record corruption; a record field is simpler. The recommendation is a ref/bookmark, with the record holding only the merge state.
