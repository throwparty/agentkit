# T-016 — gaps opened by a non-colocated jj bridge

**Question:** What gaps does a non-colocated jj bridge open, and are they acceptable?

**Answer:** C is accepted. The only external surface is the Git remote; nobody outside Litterbox reads the jj repository. A Git consumer sees the exported refs, and a conflicted jj commit is not a supported Git consumer. The remaining items are engineering obligations, not design blockers:

1. **Export the bookmark as-is.** `jj git export` writes `refs/heads/litterbox/<name>` to the bare store. A conflicted jj commit is meaningful only to jj; a Git consumer that fetches it sees the raw jj representation. Do not add a separate clean export.
2. **Surface export failures.** If `jj git export` fails, the Git view is stale; the operation reports it.
3. **Scope aborts.** The bridge's op log is shared; abort/restore uses `jj abandon`/`jj bookmark set` for the sandbox, never a global `jj op restore`.
4. **Serialise bridge operations.** A bridge-level lock covers snapshot/merge/bookmark/export; multiple workspaces share the repo.
5. **Protect the store.** `refs/jj/keep/*` keeps the trees; do not run unrelated Git maintenance on the jj store. A separate export target is not needed for the supported surface.

Non-colocation hides `.git` from the bridge and sandbox but does not remove Git storage: jj's production backend is Git, hidden inside `.jj`. That is the accepted boundary.
