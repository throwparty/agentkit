# T-013 — the current Litterbox, broken down

**Question:** What is the current module layout, where is it Git-coupled, and what has to move for one VCS-neutral trait and a `plan`-driven orchestrator?

**Answer:** The crate is 38,534 lines. The mechanism-neutral half (`sandbox/`, `backends/`) is in good shape; the VCS half is not. `scm/` is a 1,777-line Git implementation whose `Scm` trait names Git-shaped operations (branch create/delete, archive, patch, repository prefix, branch listing) and returns branch-name strings; two of those, `apply_patch` and `repo_prefix`, have no caller outside `scm`. `git2::Oid` appears only in its internals, not in the trait. `vcs_store/` is a bare-Git-clone store. `orchestrator/service.rs` (2,270 lines) imports `ThreadSafeScm`, `VcsStore` and `ScmMode`, and calls `git2::Repository::discover` directly. `domain::ScmError` wraps `git2::Error` on every variant, so the shared kernel is Git-typed too. `mcp.rs` (2,276) and `cli.rs` (1,572) are monoliths. There is no `plan`, no conflict model and no workspace-binding seam. The refactor is therefore: introduce `vcs/`, move the Git code behind the trait, add `plan.rs`, split the monoliths, then add jj.

## Current data flow

```text
MCP / CLI
  -> Sandboxes::open (orchestrator/service.rs:65)
     -> open_scm (orchestrator/service.rs:1264)
        -> ThreadSafeScm (scm/mod.rs, Git)
           -> GitScm: create_branch, make_archive, commit_snapshot
           -> VcsStore: clone_bare, install_remote, destroy_bare
        -> git2::Repository::discover (orchestrator/service.rs:915)
     -> backend (sandbox/contract.rs)
        -> create(workspace source), exec, upload, download, inspect, delete
     -> StoredSandbox (metadata_store.rs): sandbox, branch_name, remote
```

- `create`: `scm.create_branch`, `stage()` from `make_archive("HEAD")`, backend `create`, write the record.
- `snapshot`: download the workspace, `commit_snapshot_from_staging` on the branch.
- `delete`: backend delete, branch delete, bare-store destroy.
- The backend never learns about Git; the orchestrator never learns about the mechanism. That boundary is good and should stay.
- `Sandboxes::open` is the single entry point both surfaces use (`cli.rs:194`, `mcp.rs:374`); the concrete `ThreadSafeScm` is chosen inside the orchestrator, in `open_scm`.

## The mess

1. **`Scm` is a Git trait in the orchestrator's clothing.** Its methods are Git-shaped (branch create/delete, archive, patch, prefix, branch listing) and return branch-name strings. It is not reusable by jj, and `GitScm` carries `ScmMode` and `host_repo_path`. The `git2::Oid` values live in the implementation, not the trait.
2. **`VcsStore` is Git-only.** `clone_bare`, `install_remote`, `destroy_bare`; the jj bridge (T-001) needs a jj repo and `jj git export`.
3. **`StoredSandbox.remote` is the only VCS state in the record.** There is no VCS tool, no workspace binding, no merge state, no `synced` ref, no conflict state.
4. **`orchestrator/service.rs` is a 2,270-line monolith.** It mixes create/delete/exec/snapshot/listing/preflight and calls Git directly, including `git2::Repository::discover` outside the SCM module. The `plan` and state machine have nowhere to live.
5. **`mcp.rs` is a 2,276-line monolith.** Tool handlers, helpers, docs and errors in one file; adding `sandbox-status`, `sandbox-resolve`, `sandbox-conflict` and the `workspace` block would grow it.
6. **`scm/mod.rs` is a 1,777-line monolith.** Trait, Git implementation, archive, tree building, snapshot, tests.
7. **`config` has no `[vcs]` or `[workspace]`.** `GitConfig` only has `snapshot-mode`; the record has no sticky VCS/binding.
8. **`cli.rs` is 1,572 lines.** Operator conflict commands have no home.
9. **The shared kernel is Git-typed.** `domain::ScmError` wraps `git2::Error` on every variant, and `SandboxError::Scm` carries it. A backend-neutral contract cannot reuse that error type, and `git2` cannot be confined to a Git module while it lives in `domain`.
10. **Construction is split.** `open_scm` and the remote/direct choice sit in the orchestrator, and tests open `ThreadSafeScm` directly. A single construction point has to replace both.

## Target layout

```text
src/
├── vcs/                  Vcs trait, capabilities, Revision/TreeId, Conflict/Merge
│   ├── mod.rs
│   ├── git_common/       Git concepts shared by Git-backed backends: ignore matching,
│   │                     archive, tree/object primitives, path safety, naming (may use git2)
│   ├── git/              GitVcs, VcsStore, worktree/copy workspace; imports git_common, not vcs/jj
│   └── jj/               JjVcs, jj bridge, workspaces, export; imports git_common, not vcs/git
├── orchestrator/
│   ├── plan.rs           axes, classify, plan
│   ├── service.rs        create/execute/snapshot/lifecycle/listing, split further
│   └── ...
├── mcp/
│   ├── tools/            one module per tool group
│   └── ...
├── cli/                  one module per command group
├── config.rs             [vcs] tool and [vcs.<tool>] sections
└── metadata_store.rs     vcs/binding/merge fields
```

There is no separate `workspace/` module, and workspace binding and masking are not Git concepts, so they do not live in `vcs::git_common`. A backend that binds implements them in its own module: Git copies, and jj binds and masks `.jj` in `vcs::jj`.

## Refactor sequence

1. **Define the generic VCS interface and the Git common module first.** `vcs` owns the trait, capabilities, `Revision`/`TreeId`, `Merge`, `Conflict` and `ConflictSides`; `vcs::git_common` owns the Git concepts both Git-backed backends reuse (ignore matching, the snapshot filter, archive and tar materialisation, Git tree/object/ref primitives, path safety and branch naming). It may use `git2`; it is not VCS-neutral. Binding and masking stay with the backend that implements them. The contract must also express every VCS operation the orchestrator performs today, or removing `Scm` loses behaviour: branch creation and deletion, sandbox-branch enumeration, archive materialisation, snapshot commit, snapshot filtering and the remote/direct fact. `apply_patch` and `repo_prefix` are declared by `Scm` but have no caller outside it; they may be dropped. Add `arch-lint.toml` rules at the same time: `orchestrator` may import `vcs` but not `vcs::git`/`vcs::jj`/`vcs::git_common`; `vcs::git` and `vcs::jj` may import `vcs`/`vcs::git_common` but not each other; `vcs::git_common` imports neither backend. `cli`/`mcp` reach VCS only through the orchestrator.
2. **Adapt the existing Git implementation to the interface.** Move `GitScm`/`VcsStore` under `vcs::git`, keep behaviour, and prove the interface with the Git backend. No jj code yet.
3. **Build the plan/conflict surface on the interface with Git `Blocking`.** Axes, `plan`, the `workspace` block, `sandbox-status`/`sandbox-resolve`/`sandbox-conflict`, and the operator commands.
4. **Add the jj backend later.** `vcs::jj` implements the same interface and uses `vcs::git_common`; it never calls `vcs::git`, and `vcs::git` never calls `vcs::jj`. The non-colocated bridge, workspaces, `.jj` masking and native conflicts are jj's implementation.
5. **Add config/record fields and legacy handling (T-010).** `[vcs] tool` with per-VCS sections (T-010), and `vcs`/`binding` in `StoredSandbox`, missing = Git + Copied facts.

The interface is the first deliverable; the Git adapter proves it; jj is a later implementation of the same contract. This avoids tangling the two and gives the arch-lint rules something concrete to enforce.
