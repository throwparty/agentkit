# T-013 — the current Litterbox, broken down

**Question:** What is the current module layout, where is it Git-coupled, and what has to move for one VCS-neutral trait and a `plan`-driven orchestrator?

**Answer:** The crate is ~38.5k lines. The mechanism-neutral half (`sandbox/`, `backends/`) is in good shape; the VCS half is not. `scm/` is a 1,777-line Git implementation with a trait that returns `git2::Oid`; `vcs_store/` is a bare-Git-clone store; `orchestrator/service.rs` (2,270 lines) imports `ThreadSafeScm`, `VcsStore` and `ScmMode` directly and does branch creation, staging, snapshots and deletion; `mcp.rs` (2,276) and `cli.rs` (1,572) are monoliths. There is no state machine, no `plan`, no conflict model, and no workspace-binding seam. The refactor is therefore: introduce `vcs/` and `workspace/`, move the Git code behind the trait, add `plan.rs`, split the monoliths, then add jj.

## Current data flow

```text
MCP / CLI
  -> Sandboxes (orchestrator/service.rs)
     -> ThreadSafeScm (scm/mod.rs, Git)
        -> GitScm: create_branch, make_archive, commit_snapshot
        -> VcsStore: clone_bare, install_remote, destroy_bare
     -> backend (sandbox/contract.rs)
        -> create(workspace source), exec, upload, download, inspect, delete
     -> StoredSandbox (metadata_store.rs): sandbox, branch_name, remote
```

- `create`: `scm.create_branch`, `stage()` from `make_archive("HEAD")`, backend `create`, write the record.
- `snapshot`: download the workspace, `commit_snapshot_from_staging` on the branch.
- `delete`: backend delete, branch delete, bare-store destroy.
- The backend never learns about Git; the orchestrator never learns about the mechanism. That boundary is good and should stay.

## The mess

1. **`Scm` is a Git trait in the orchestrator's clothing.** It returns `git2::Oid`, exposes `Repository`-shaped concepts, and `GitScm` carries `ScmMode` and `host_repo_path`. jj cannot implement it without rewriting the trait.
2. **`VcsStore` is Git-only.** `clone_bare`, `install_remote`, `destroy_bare`; the jj bridge (T-001) needs a jj repo and `jj git export`.
3. **`StoredSandbox.remote` is the only VCS state in the record.** There is no VCS tool, no workspace binding, no merge state, no `synced` ref, no conflict state.
4. **`orchestrator/service.rs` is a 2,270-line monolith.** It mixes create/delete/exec/snapshot/listing/preflight and calls Git directly. The `plan` and state machine have nowhere to live.
5. **`mcp.rs` is a 2,276-line monolith.** Tool handlers, helpers, docs and errors in one file; adding `sandbox-status`, `sandbox-resolve`, `sandbox-conflict` and the `workspace` block would grow it.
6. **`scm/mod.rs` is a 1,777-line monolith.** Trait, Git implementation, archive, tree building, snapshot, tests.
7. **`config` has no `[vcs]` or `[workspace]`.** `GitConfig` only has `snapshot-mode`; the record has no sticky VCS/binding.
8. **`cli.rs` is 1,572 lines.** Operator conflict commands have no home.

## Refactor sequence

1. **Define the generic VCS interface and the shared module first.** `vcs` owns the trait, capabilities, `Revision`/`TreeId`, `Merge`, `Conflict` and `ConflictSides`; `vcs::common` owns the neutral algorithms both backends can use (ignore matching, archive/tar materialisation, path safety, workspace binding/masking, branch naming). Add `arch-lint.toml` rules at the same time: `orchestrator` may import `vcs` but not `vcs::git`/`vcs::jj`; `vcs::git` and `vcs::jj` may import `vcs`/`vcs::common` but not each other; `vcs::common` imports neither backend. `cli`/`mcp` reach VCS only through the orchestrator.
2. **Adapt the existing Git implementation to the interface.** Move `GitScm`/`VcsStore` under `vcs::git`, keep behaviour, and prove the interface with the Git backend. No jj code yet.
3. **Build the plan/conflict surface on the interface with Git `Blocking`.** Axes, `plan`, the `workspace` block, `sandbox-status`/`sandbox-resolve`/`sandbox-conflict`, and the operator commands.
4. **Add the jj backend later.** `vcs::jj` implements the same interface and uses `vcs::common`; it never calls `vcs::git`, and `vcs::git` never calls `vcs::jj`. The non-colocated bridge, workspaces, `.jj` masking and native conflicts are jj's implementation.
5. **Add config/record fields and legacy handling (T-010).** `[vcs] tool`, `[workspace] binding`, `vcs`/`binding` in `StoredSandbox`, missing = Git + Copied facts.

The interface is the first deliverable; the Git adapter proves it; jj is a later implementation of the same contract. This avoids tangling the two and gives the arch-lint rules something concrete to enforce.
