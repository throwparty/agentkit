# T-002 — masking `.jj` on a bound jj workspace

**Question:** Can a jj workspace be bind-mounted into a sandbox with `.jj` masked on bubblewrap, Docker and Seatbelt?

**Answer:** Bubblewrap and Docker can hide the **contents** of `.jj` on this Linux host; the directory entry remains as an empty mountpoint. Bubblewrap uses `--tmpfs <workspace>/.jj` over the bound workspace; Docker uses an empty volume at `/workspace/.jj`. In both cases the workspace files are present, `.jj` is empty, and the sandbox has no read or write access to the VCS data. If the directory name itself must be absent, an overlay/whiteout or a filtered view is required; an empty mountpoint is not absence. Seatbelt is macOS-only and was not probed here, so it is unproven rather than assumed.

## Reproduction

`probe.sh` creates a non-colocated jj bridge and one workspace, then runs bubblewrap and Docker with the workspace bound and `.jj` masked. Run:

```sh
bash maps/2026-11-18-litterbox-vcs-history-sync/evidence/T-002/probe.sh
```

Raw output: [`output.txt`](output.txt).

Key observations:

- `bwrap --ro-bind / / --bind <ws> <ws> --tmpfs <ws>/.jj --chdir <ws>` sees `README.md`, sees `.jj` as an empty directory, and cannot read the VCS.
- `docker run -v <ws>:/workspace -v <empty>:/workspace/.jj <image> ...` has the same result.
- Seatbelt is recorded as `unprobed: macOS-only; this host is Linux`.

**Implication:** `Bound` can honour “no VCS access” on bubblewrap and Docker by masking contents. The capability report must distinguish “contents hidden” from “path absent”; only the former is proved. A backend that cannot mask at all must refuse `Bound` for a VCS whose metadata lives in the workspace.
