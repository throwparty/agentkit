# T-021 — falling back when the bridge tip is conflicted

**Question:** When the bridge tip is a conflicted revision, does the sandbox fall back to the last non-conflicted history, and at which points does it check?

**Answer:** Yes. The conflict stays in the user's local copy and the bridge; the sandbox never adopts a conflicted tip. On every operation that touches the workspace or reads source state, the sandbox reads the bridge tip, asks the VCS whether it is conflicted, and holds at `synced` and the sandbox branch when it is. It adopts only a non-conflicted tip. The main workspace therefore stays on the last good tree and remains buildable. The check is lazy; there is no watcher or timer.

## Workflow

1. The user rewrites or merges their local `litterbox/<name>` and pushes it to the bridge. jj may leave the commit conflicted; Git is normally resolved before the push.
2. A sandbox operation reads the bridge tip.
3. If the tip is conflicted: do not adopt. Keep `synced` and the sandbox branch; report `held` with the tip and the conflict paths. The agent continues on the last good tree.
4. The sandbox's own snapshots continue on the sandbox branch; the shared branch is not advanced.
5. The user resolves locally and pushes a non-conflicted tip. The next operation re-checks and adopts.
6. If the sandbox has changes when the resolved tip arrives, the existing divergence hold applies; the user merges the sandbox branch into their resolution.

## Reproduction

`probe.sh` builds a jj repository with a base, a sandbox branch and a user branch; merges the user and sandbox branches so the user bookmark is conflicted; shows the sandbox branch is clean and readable; resolves the bridge conflict in the working copy; shows the bridge tip clean. It also creates a Git commit with conflict markers, scans it, resolves it, and scans again. Run:

```sh
bash maps/2026-11-18-litterbox-vcs-history-sync/evidence/T-021/probe.sh
```

Key observations:

- The jj bridge tip reports `conflicted` and `file.txt    2-sided conflict`; the sandbox bookmark reports `clean` and `No conflicts found`.
- The fallback decision is `HOLD: bridge tip is conflicted; the sandbox stays on its last non-conflicted revision`.
- After `jj edit` and editing `file.txt`, the bridge tip reports `clean` and the decision is `ADOPT: bridge tip is clean; the next sandbox operation adopts it`.
- The Git marker scan finds `<<<<<<<`, `=======`, `>>>>>>>` and reports `HOLD`; after resolution it reports `ADOPT`.

**Implication:** the build problem disappears because the agent's workspace is never the conflicted tree. The conflict is a property of the bridge tip, not the sandbox.
