# T-010 — VCS and workspace-binding configuration, and migration

**Question:** What is the migration and configuration path for VCS selection and workspace binding on existing records?

**Revised 2026-11-19, during ADR alignment:** binding is no longer a global `[workspace]` key. Each VCS owns a configuration section, mirroring how a compute backend is selected and configured (`[backends.<name>]`). The trait therefore takes no binding argument; the constructed backend knows its own binding behaviour.

**Revised 2026-11-21, during implementation:** the section is a *workspace* setting in the untracked `.agentkit/litterbox/config.local.toml`, not machine-wide user configuration. A machine hosts many workspaces, so one user file cannot carry a different VCS and binding for each of them. The committed project file still may not set it, and the user configuration is refused with a message naming the local override, as `vcs` now has its own clause in `reject_project_keys_in_user`. `snapshot-mode` moved into `[vcs.git]` with it, which makes it a workspace setting rather than project configuration. The `tool` selector is not implemented yet: Git is the only backend, so composition reads `[vcs.git]` directly and `[vcs] tool` lands with `[vcs.jj]`. `create` refuses when `binding` is missing, which is what the selector's refusal becomes once there is a second tool.

**Answer:** Both settings are sticky per sandbox. `[vcs] tool = "git" | "jj"` selects the tool, and each tool owns a configuration section parsed and validated by that backend (`[vcs.git]`, `[vcs.jj]`), mirroring the backend selector and `[backends.<name>]`; the selected section supplies binding. Values live in the workspace's untracked local override (`.agentkit/litterbox/config.local.toml`); the committed project file may not set them, and the user configuration is refused rather than noticed. A new sandbox must choose a tool: `create` refuses with a configuration error naming the key, but `list`, `delete`, `pause` and `resume` still work. The chosen tool and the resulting binding are written into `StoredSandbox`, so later config changes affect only new sandboxes. Existing records have neither field; they load as `Current` and are treated as **legacy facts**: `tool = git` and `binding = copied`, because that is how they were created. An unsupported combination (`bound` with Git) is refused when the configuration is validated, before create, never defaulted to copying; a `jj` request on a project whose bridge is a Git bare clone is refused with a migration remedy, never silently converted.

## Code facts

- `StoredSandbox` is the persisted record plus the branch; it currently has `sandbox`, `branch_name` and `remote` (`crates/agentkit-litterbox/src/metadata_store.rs:18-25`). There is no VCS or binding field.
- `LoadedSandbox` has `Current` and `Corrupt` only (`metadata_store.rs:29-39`); there is no separate legacy variant in this checkout, so old records are `Current` and must load through serde defaults.
- `ProjectFile` already carries machine-owned fields (`backend`, `forwarding`, `store-view`, `accept-degraded`, setup consent) and `merge` ignores or refuses them when the committed project file sets them (`config.rs:353-426`). `store_view` is the model to copy: a machine-owned option with a default (`config.rs:374-375`, `config.rs:406-412`).
- The backend pattern to mirror: a machine-owned selector (`backend`) plus one untyped section per backend (`Config.backend_settings: BTreeMap<String, toml::Value>` and `ProjectFile.backends`, `config.rs:67-68` and `368-370`), parsed by each backend's own config module.
- `Config` carries the merged values, including `git: GitConfig` and `store_view` (`config.rs:64-90`); `GitConfig` currently has only `snapshot-mode` (`config.rs:56-62`).
- `merge` builds the final `GitConfig` and `store_view` from the local file (`config.rs:479-486`).
- `Sandboxes::create` reads `self.config` and writes `StoredSandbox` (`orchestrator/service.rs`); `stored()` loads the record for every later operation. That is the seam for sticky values.

## Proposal

```toml
# ~/.config/agentkit/litterbox/config.toml (machine-owned)
[vcs]
tool = "git"               # or "jj"

[vcs.git]
snapshot-mode = "remote"   # the existing GitConfig, as this tool's section

[vcs.jj]
binding = "bound"          # or "copied"; Git has no binding key
```

```rust
pub struct StoredSandbox {
    pub sandbox: SandboxRecord,
    pub branch_name: String,
    pub remote: bool,
    #[serde(default)]
    pub vcs: Option<VcsTool>,          // None = legacy fact: Git
    #[serde(default)]
    pub binding: Option<WorkspaceBinding>, // None = legacy fact: Copied
}
```

Rules:

1. `create` requires `[vcs] tool`; missing is a configuration error, not a default.
2. The chosen values are written into the record; later operations read the record, not the current config.
3. A record with `None` is a legacy sandbox: `Git` + `Copied`, reported as a legacy fact, never rewritten.
4. Binding belongs to the selected tool's section. A combination that tool cannot honour (`binding = "bound"` with Git) is a configuration error when validated, before any sandbox is created; there is no runtime fallback to copying.
5. `vcs = "jj"` is refused when the project's bridge is a Git bare clone; the remedy is a new project/bridge or an explicit migration, never a silent conversion.
6. `list`/`delete`/`pause`/`resume` never require the new config keys; only `create` does.
7. Moving `snapshot-mode` from `[git]` into `[vcs.git]` is a configuration migration; whether `[git]` is accepted as a deprecated alias is decided when the keys land, not in the VCS-interface ADR.

Consequence for the interface: `prepare` takes no `WorkspaceBinding` argument. The composition point reads `[vcs] tool` and that tool's section, constructs the backend, and `Capabilities` reports the binding behaviour the configuration produced. This is why the interface ADR declares the type but neither passes it per call nor falls back at runtime.
