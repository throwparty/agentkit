# T-040: does every recorded mount mean the sandbox is usable?

**Question.** T-039 shows the status document arrives before the view is built.
Is "every recorded mount is present at its recorded path with its recorded
access" a safe readiness check for create, or does it fire before a command can
run?

**Method.** Start the 1779-bind view from T-035. Poll
`/proc/<sandbox-pid>/mountinfo` every 5ms until all 1779 store paths are
present. Record the time, whether `/oldroot` is still mounted, and the options
on `/src`. Then attempt a join immediately and record whether the first attempt
succeeds. Reproduce with `evidence/T-040-readiness-probe.sh`.

**Observation.** Four runs, bubblewrap 0.12.0, kernel 7.2.15.

```
run 1: status 38ms, all mounts present 5045ms, first exec 5076ms, gap 31ms
run 2: status 56ms, all mounts present 4986ms, first exec 5020ms, gap 34ms
run 3: status 58ms, all mounts present 4600ms, first exec 4628ms, gap 28ms
run 4: status 58ms, all mounts present 4922ms, first exec 4950ms, gap 28ms

at that instant, /oldroot mounts: 0
at that instant, /src options: rw,nosuid,nodev,noatime
```

The first join succeeded on its first attempt in every run, 28 to 34ms after the
last mount appeared. That gap is the join itself, not a wait.

**Conclusion.** Yes. When the last recorded path appears, the old root is
already detached and a command runs. create can poll for the recorded mounts
instead of guessing a delay, and the check it uses is the same one a later join
makes.

The check must compare against the mounts create rendered, and it must tolerate
the mounts bwrap makes for itself, which are its own proc, dev and tmpfs
entries rather than host paths.
