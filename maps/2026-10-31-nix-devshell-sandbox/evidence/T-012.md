# T-012: does a second command share a live context?

**Question.** Do successive commands in the same sandbox share a live execution
context, or only the filesystem, on each backend?

**Method.** Reading of primary sources already in the tree. No new execution.

- `adrs/2026-10-31-linux-bwrap-sandbox/poc/argv/default.txt`, the emitted argv
  for the default view, which is the fixture the golden test asserts.
- `adrs/2026-10-31-linux-bwrap-sandbox/findings.md`, for what the namespaces
  leave reachable.
- `adrs/2026-10-31-darwin-app-sandbox/findings.md` and `spec.toon` EC-009, for
  what the macOS mechanism does and does not create.
- `crates/agentkit-litterbox/src/sandbox/mod.rs`, for the current model:
  `create` starts `tail -f /dev/null` as the container's top-level process and
  every `shell` call is a `compute.exec` against the same `container_id`.

**Observation.** The Linux argv contains `--unshare-user`, `--unshare-pid`,
`--unshare-ipc`, `--unshare-uts`, `--unshare-cgroup`, `--unshare-net` and
`--die-with-parent`. Each exec is a fresh `bwrap` invocation, so each exec gets
its own mount, pid and network namespace. `--die-with-parent` states the
lifetime rule: the sandbox exists exactly as long as that invocation's process
tree. The workspace is a bind mount of a host directory (`--bind <FD> /src`),
so it outlives the invocation; nothing else does.

The macOS findings state there is no mount or pid namespace at all, and the
spec's EC-009 records that enforcement happens at resource acquisition in the
shared kernel. The helper applies a profile to itself and execs; there is no
object created that a later process could join or not join.

Applying this to the three backends, for a second command started after the
first:

| What the second command shares | Docker | macOS `sandbox_init` | per-exec `bwrap` |
|---|---|---|---|
| Workspace files | yes (bind) | yes (host directory) | yes (bind) |
| Home / scratch state | yes (container fs) | yes (host, subject to profile) | yes, if the sandbox home is a host directory |
| Process table | yes (shared pid ns) | yes (host pid space) | no (`--unshare-pid`) |
| Network namespace | yes (container netns) | yes (host network) | no (`--unshare-net`) |
| Can signal command 1's processes | yes | yes, subject to `signal` rule | no |
| Can reach command 1's `127.0.0.1:port` | yes | yes, if granted `localhost:port` | no, distinct loopback |
| Docker-style `pause` applies to the sandbox | yes | no | no |

**Conclusion.** Docker and the macOS sandbox both give successive commands a
shared live context; per-exec `bwrap` gives only a shared filesystem. The
divergence is not persistence of files — all three have that — it is the pid
and network namespaces, which are created per exec on Linux and therefore
cannot be shared without either joining a live sandbox or holding one open.

The practical consequence is the reverse of the intuitive one: on the two
backends that are *more* confined by namespaces, cross-command interaction is
absent; the macOS backend, which cannot isolate pids or the network at all,
behaves most like the Docker model the product already assumes.
