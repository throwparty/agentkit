# T-021: where must the egress proxy sit on macOS?

**Question.** Given that the macOS profile accepts only `localhost` and `*` as a
host token, where must an egress proxy sit so a sandboxed command can reach it?

**Method.** Two placements, each with a real listener started outside the
sandbox and a real client inside it.

```
A. loopback TCP
   host:  python3 -m http.server <port> --bind 127.0.0.1
   sandbox: python3 client.py <port>   with and without --connect localhost:<port>

B. unix socket in the workspace
   host:  python3 unix-server.py /private/tmp/lbx-t017/ws/sock/proxy.sock
   sandbox: python3 client.py /private/tmp/lbx-t017/ws/sock/proxy.sock
```

**Observation.**

```
A. with grant      HTTP/1.0 200 OK
A. without grant   PermissionError: [Errno 1] Operation not permitted
B. unix socket     PermissionError: [Errno 1] Operation not permitted
```

The unix socket file is inside the workspace, is mode 0666, and the sandbox
grants the workspace read-write. Connecting to it still fails with `EPERM`,
because `connect(2)` on an `AF_UNIX` socket is a `network-outbound` operation
with a `(remote unix-socket …)` filter, and the process also needs
`(allow system-socket (socket-domain AF_UNIX))` to create the socket. The
profile emits neither; a readable socket file is not sufficient.

**Conclusion.** On macOS the proxy must listen on a **loopback TCP port**, and
the profile must grant `localhost:<port>` for it. That is the same shape the
egress harness already exercises, now against a real proxy rather than a test
server.

The Linux placement does not carry over. On Linux the proxy sits outside the
network namespace and is reached through a bind-mounted unix socket (T-014),
because the namespace has no route to the host. On macOS there is no network
namespace — every command runs on the host stack (T-020) — so loopback is
reachable directly and the unix-socket trick is unnecessary as well as blocked.

Consequences for the Darwin provider:

- The profile needs one `localhost:<port>` grant per proxy, which is what
  `--connect` already expresses, and no `network-bind` or `network-inbound`.
- A unix-socket transport would require adding `system-socket` and
  `network-outbound (remote unix-socket …)` rules. That is possible, but it buys
  nothing here: the proxy is on the same host and loopback is already granted.
- The proxy must bind a port that is free when the sandbox starts; the grant is
  per port, so a proxy that moves ports changes the profile.
