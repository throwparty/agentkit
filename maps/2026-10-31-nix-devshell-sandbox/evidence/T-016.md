# T-016: does a captured devShell environment build inside the holder?

**Question.** With the differential capture from T-011 and no network, does a
real build run inside a bwrap holder?

**Method.** A holder with the production namespace set, the host store bound
read-only, no network, a private home, and the captured environment applied by
`execve` in the joined process:

```bash
bwrap --unshare-user --unshare-pid --unshare-ipc --unshare-uts \
      --unshare-cgroup --unshare-net --disable-userns --clearenv \
      --ro-bind /nix/store /nix/store \
      --ro-bind /run/current-system /run/current-system \
      --ro-bind /etc /etc --proc /proc --dev /dev --tmpfs /tmp \
      --dir /home/sandbox --setenv HOME /home/sandbox \
      --bind "$REPO" "$REPO" --chdir "$REPO" \
      --json-status-fd 3 -- sleep infinity
```

then, from outside:

```bash
nsenter -t "$PID" -U -i -n -p -m -u --preserve-credentials \
        -r"/proc/$PID/root" -W"$REPO" -- python3 -c "$EXEC"
```

where `$EXEC` reads the captured `VAR=value\0` list and calls `execvpe`. That is
what the join helper will do in production: apply the environment at exec, not by
inheriting the caller's.

**Conclusion.** Yes. A devShell built by `cargo build` and `cargo test` inside
the holder, with a read-only store, no network and a private home, using only
the 89 variables captured on the host. No package installation, no network
fetch, no daemon.

Attendance notes:

- **The workspace was bound at its host path**, because `CARGO_HOME`,
  `RUSTUP_HOME` and the leading entry of `PATH` are absolute paths into the
  checkout, and cargo needs a writable cargo home. Binding at `/src` instead
  requires rewriting references to the *workspace* in the captured environment.
  Store paths, including the `NIX_*` toolchain and sysroot paths, must stay
  unchanged, because `/nix/store` is mounted at the same path inside the
  sandbox. This is the main open shape question for the provider, not a doubt
  about the mechanism.
- The build wrote `target/` inside the host checkout, which is the workspace
  grant working as intended. A production provider materialises a workspace
  directory rather than binding the project tree.
- **No network was needed** because the registry cache lives in the checkout's
  `.cargo`, which the workspace grant exposes. A project whose first build
  fetches from crates.io will fail, exactly as it would on a host with no
  network.
- `cargo` resolved through `rustup` to the Nix toolchain, so the four
  hook-supplied variables are load-bearing. Dropping `RUSTUP_HOME` or
  `CARGO_HOME` breaks the build; this is the concrete justification for the
  differential capture rather than `print-dev-env` alone.
