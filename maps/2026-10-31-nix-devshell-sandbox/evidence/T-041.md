# T-041: can a process join the sandbox in-process, and in what order?

**Question.** T-013 and T-024 proved a join with `nsenter`. Can the backend do
the same in its own process, and does the namespace order that `nsenter`
accepts work when the calls are made directly?

**Method.** `evidence/T-041-namespace-order.py` starts a holder as in T-033,
prints the owner of every namespace with `NS_GET_USERNS`, and tries both orders.
`evidence/T-041-join-probe.py` then runs the full join with the working order:
open the seven namespace descriptors and a descriptor for the sandbox root,
join the user namespace that owns the others, the six namespaces, and the
sandbox's user namespace, fork again so the command is a member of the pid
namespace, chroot through the pinned root descriptor, and exec.

**Observation.**

The first attempt joined the sandbox's own user namespace first, as `nsenter
-U` does, and every later join failed:

```
join: setns ipc failed: Operation not permitted
uid_map: 1000       1000          1
```

`setns` on the sandbox's user namespace succeeded and granted a full capability
set, but the ipc, net, pid, mnt, uts and cgroup namespaces are owned by its
parent user namespace, not by the sandbox's own. The owner of each was read with
`NS_GET_USERNS`:

```
holder userns: user:[4026534770]
user owner userns: user:[4026534710]
ipc owner userns: user:[4026534710]
net owner userns: user:[4026534710]
pid owner userns: user:[4026534710]
mnt owner userns: user:[4026534710]
uts owner userns: user:[4026534710]
cgroup owner userns: user:[4026534710]
```

Joining the parent first, then the six namespaces, then the sandbox's user
namespace, succeeds:

```
base: rc=0
ipc: rc=0
net: rc=0
pid: rc=0
mnt: rc=0
uts: rc=0
cgroup: rc=0
user: rc=0
```

The full join then runs a command:

```
holder: 369700  sandbox: 369701
view ready
joined command exit: 0
joined pid namespace:   pid:[4026534836]
sandbox pid namespace:  pid:[4026534836]
joined is a member:     yes
joined cgroup namespace: same as sandbox
joined uid:             1000
```

**Conclusion.** Yes, in-process, and the order is not the one `nsenter` accepts.
`nsenter` joins the user namespace and then the others, and succeeds because it
resolves the namespaces as the same uid; the kernel's capability check is
against the namespace that owns each target, which here is the sandbox user
namespace's parent. A direct join must enter that parent first.

Two further requirements follow from the probe. Every descriptor must be opened
before the first join, because joining the mount namespace replaces `/proc`.
The chroot must go through the root descriptor opened beforehand, because
`/proc/<pid>/root` stops resolving once the mount namespace is the sandbox's.
