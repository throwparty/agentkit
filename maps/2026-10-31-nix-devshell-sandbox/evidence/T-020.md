# T-020: does the macOS sandbox share a live context across commands?

**Question.** Do successive commands in a macOS sandbox share pid and network
context, or only the filesystem?

**Method.** Citation from the Darwin spike; no new execution.

- `adrs/2026-10-31-darwin-app-sandbox/spec.toon` EC-009: "There is no mount or pid
  namespace, no CPU or memory quota, no uid separation, no syscall filtering, and
  hostname rules match resolved addresses."
- `adrs/2026-10-31-darwin-app-sandbox/findings.md`: the helper applies a profile
  to itself and execs; enforcement happens at resource acquisition in the shared
  kernel.
- The same file's egress section: `localhost:8765` connects when granted, a
  second local server on `8766` is refused, and no destination can be named at
  all.

**Observation.** Nothing is created that a later command could join or not join.
The profile is a per-process property, inherited by descendants. A second command
is a second helper invocation, and it runs in the host's pid space with the host's
network stack; only the paths its profile allows differ.

**Conclusion.** Yes. The macOS sandbox shares pid and network context with every
other command and with the host, because it has no namespaces to separate them.
Cross-command **client** traffic works for that reason — a sandboxed command can
connect to anything its profile grants.

Sharing the host network stack does not, however, prove that a sandboxed
*listener* is reachable. Server-side operations are policy-gated too, and the
profile the spike shipped starts from `deny default` and emits neither
`network-bind` nor `network-inbound`. The recorded egress probe only exercises a
sandboxed client connecting to an unsandboxed server, never the reverse. So
listener reachability is **untested**: it is expected to work once explicit
server grants are added, but nothing in the evidence establishes it, and a
sandboxed server would in any case be exposed on the host's loopback to every
other host process, which is the opposite of the isolation the Linux backend
gets.
