# T-024: does a holder survive the process that created it?

**Question.** Every probe so far joined a holder that its launcher was still
keeping alive. The CLI is one process per command. Does a bwrap holder survive
the short-lived process that created it, so a later process can join it?

**Method.** NixOS, kernel 7.2, bubblewrap 0.12.0, unprivileged user. A `bash -c`
launches the holder, writes bwrap's status document to a file, and exits. A
second shell then reads `child-pid` from that file and joins with `nsenter`.

Reproduce with the probe beside this file:

```bash
bash maps/2026-10-31-nix-devshell-sandbox/evidence/T-024-holder-survival.sh
```

Its core, condensed:

```bash
BWRAP=$(nix build --no-link --print-out-paths nixpkgs#bubblewrap)/bin/bwrap
bash -c '
  exec 3>"$STATUS"
  "$BWRAP" --unshare-user --unshare-pid --unshare-ipc --unshare-uts \
    --unshare-cgroup --unshare-net [--die-with-parent] \
    --clearenv --setenv PATH /run/current-system/sw/bin \
    --ro-bind /nix/store /nix/store \
    --ro-bind /run/current-system /run/current-system \
    --ro-bind /etc /etc \
    --proc /proc --dev /dev --tmpfs /tmp \
    --bind "$ROOT" /src --chdir /src \
    --json-status-fd 3 -- sleep 300 &
'
# launcher has exited; read child-pid from $STATUS and:
nsenter -t "$CHILD" -U -i -n -p -m -u --preserve-credentials \
  -r"/proc/$CHILD/root" -W/src -- /run/current-system/sw/bin/id
```

## Observation

Both variants survived the launcher's exit and were joined from a later process.

```
=== with --die-with-parent
launcher exited: 0
holder processes still alive after launcher exit:
  1190882 bwrap --unshare-user ... --die-with-parent ...
  1190884 bwrap --unshare-user ... --die-with-parent ...
  1190885 sleep 300
child-pid from status: 1190884
  join: uid=1000 gid=1000 groups=1000,65534(nogroup)

=== without --die-with-parent
launcher exited: 0
holder processes still alive after launcher exit:
  1190900 bwrap --unshare-user ...
  1190902 bwrap --unshare-user ...
  1190903 sleep 300
child-pid from status: 1190902
  join: uid=1000 gid=1000 groups=1000,65534(nogroup)
```

`--die-with-parent` ties the sandbox command to bwrap: if bwrap dies, the
command dies. It does not tie bwrap to the launcher, so it does not kill a
holder whose creator has exited. T-013's teardown already kills pid 1 to end
the namespace.

## Conclusion

Yes. A holder created by a one-shot CLI process outlives it, and a later process
joins it by the `child-pid` bwrap reported. The backend must still detach the
holder's standard streams when it creates one: in this probe they were inherited
from a shell that stayed alive, and a caller reading a pipe to EOF would
otherwise wait on descriptors the holder keeps open. Detaching them is an
implementation detail, not a survival problem.
