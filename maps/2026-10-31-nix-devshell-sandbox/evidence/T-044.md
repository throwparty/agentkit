# T-044. Does a closure-sized profile of read grants fit?

Answer: no for a per-path closure. 238 grants apply but cost about 43 ms per
command (4× the prototype's 12 ms); 1779 grants are rejected outright. Seatbelt
caps the serialised profile at 65,535 bytes, which is about 1,010 real store
paths, and cost grows superlinearly before that: ~44 µs per grant at 238,
~400 µs at 800. On macOS the devShell closure must be collapsed to a coarser
read grant rather than rendered path by path.

Host: macOS 27.2.1 (26B131), arm64. Probed 2026-11-14.

## Reproduce

Source `T-044-scale.c`, built as `cc -O2 -o build/scale T-044-scale.c` from
this directory. It reads distinct real
paths from `/nix/store`, renders `deny default` plus a platform baseline plus
one `(subpath "<store path>")` read rule per path, then times
`fork + sandbox_init + execv /usr/bin/true + waitpid` over 30 runs.

```
./scale --bare  --n 238 --runs 30
./scale --n 1 --runs 30
./scale --n 238 --runs 30
for n in 400 600 800 1000 1005 1010 1015 1779 5000 10000; do ./scale --n $n --runs 3; done
```

Store facts: 75,017 directory entries, 75,013 distinct real paths.

## Cost

| N grants | Profile bytes | Median ms | p95 ms |
|---:|---:|---:|---:|
| bare (no sandbox) | 0 | 4.03 | 4.67 |
| 1 | 457 | 11.46 | 12.33 |
| 238 | 20,226 | 42.70 | 43.55 |
| 400 | n/a | 95.47 | 98.31 |
| 600 | n/a | 197.18 | 200.78 |
| 800 | n/a | 337.67 | 337.95 |
| 1,000 | n/a | 513.60 | 513.72 |
| 1,010 | n/a | 525.27 | 525.45 |

The prototype's whole-store profile is one grant and applies in 11 to 12 ms. The
T-022 closure of 238 paths raises that to about 43 ms; a 1,000-path closure costs
half a second per command. There is no warm-up outlier. The first sample is the
minimum, so this is per-apply cost, not one-off policy installation.

## The ceiling

| N | Result |
|---:|---|
| 1,010 | applies; 519 to 525 ms |
| 1,015 | `sandbox_init: data object length 65801 exceeds maximum (65535)` |
| 1,779 | `sandbox initialization failed: data object length 114771 exceeds maximum (65535)` |
| 5,000 | `Assertion failed: (diff <= INSTR_JUMP_NE_MAX_LENGTH), function push_jne_instr, file serialize.c, line 240` (child caught SIGABRT) |
| 10,000 | `sandbox_init: compilation failed` |

The limit is on the serialised profile, not a rule count, so it moves with path
length. The 5,000 case is worse than a rejection: libsandbox aborts on an
assertion, so a backend that renders without a bound can crash a child rather
than fail closed.

## Semantics

A granted store path is readable and an ungranted one is not:

```
$ helper --workspace <ws> --read /nix/store/00067...-lame-3.100.tar.gz.drv -- /bin/cat <path>
Derive([("out","/nix/store/hrm55whlbjsmr...
$ helper --workspace <ws> -- /bin/cat /nix/store/zzz9...-check-link-targets.sh.drv
cat: /nix/store/zzz9...-check-link-targets.sh.drv: Operation not permitted
```

`ls <path>` alone is **not** a semantics check: `file-read-metadata` is
unqualified, so stat succeeds on an ungranted path and `ls` prints it. Only a
read of content distinguishes granted from ungranted.

## What this means for D

1. Rendering `Contributions.mounts` one rule per path is not viable for a
   closure above a few hundred paths. The backend needs a policy: collapse the
   contribution to its common ancestor when the list exceeds a budget, which is
   mechanism-neutral and not a Nix special case. For a devShell that ancestor is
   `/nix/store`, so the rendered result coincides with `StoreView::Whole`.
1. The contract already supports both forms (`StoreView::Closure` and `Whole`),
   but D must state what the macOS renderer does when closure rendering is
   rejected for size, rather than failing the sandbox.
1. The 65,535-byte ceiling should be enforced in the renderer, before
   `sandbox_init`, because some over-size profiles abort libsandbox instead of
   returning an error.
1. Closure-shaped mounting controls read visibility on Linux, where the mount
   namespace hides unlisted paths. macOS has no namespace, so the grant list is
   the only visibility control, and at 43 ms per command it is expensive.

## Caveats

- The probe grants store entries that are not used by the command, so the cost
  is profile application, not execution.
- `/usr/bin/true` is platform-only; a real command that reads a granted store
  path adds its own I/O. The table is the confinement overhead.
- Only read grants were varied. Adding write grants or mach names moves the
  ceiling down, because the 65,535-byte limit is on the whole serialised
  profile.
