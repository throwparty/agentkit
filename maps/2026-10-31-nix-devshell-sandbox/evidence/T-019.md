# T-019: freezing commands that live outside the holder's cgroup

**Question.** Can commands joined into a holder be frozen and limited when they
are started outside the holder's cgroup, or is only the first command covered?

**Method.** Two probes on NixOS, kernel 7.2.14, bubblewrap 0.12.0, systemd user
manager with cgroup v2 delegation.

## Test A: enumerate by pid namespace, stop and resume every member

A holder was started with `--unshare-pid`, then three commands were joined: two
long sleeps directly, and one that calls `setsid` to daemonise itself so it
leaves the session and process group.

```bash
NS=$(readlink /proc/$HOLDER_CHILD/ns/pid)
for p in /proc/[0-9]*; do
  [ "$(readlink "$p/ns/pid" 2>/dev/null)" = "$NS" ] && kill -STOP "${p#/proc/}"
done
```

```
sandbox pid ns: pid:[4026534577]
--- processes whose pid namespace is the sandbox:
  host pid 91407 comm=bwrap  state=S
  host pid 91408 comm=sleep  state=S
  host pid 91416 comm=sleep  state=S
  host pid 91417 comm=sleep  state=S
  host pid 91418 comm=sleep  state=S      <- the setsid daemon
--- SIGSTOP every member:
  91407 state=T  91408 state=T  91416 state=T  91417 state=T  91418 state=T
--- SIGCONT:
  91407 state=S  91408 state=S  91416 state=S  91417 state=S  91418 state=S
```

Every member is found, including the one that daemonised. Pid namespace
membership cannot be changed by the process itself, so this cannot be evaded by
`setsid`, `fork` or double-fork.

## Test B: move an outside process into the sandbox's scope

```bash
systemd-run --user --scope --unit=t019-probe -- sleep 30 &
U=$(systemctl --user show t019-probe.scope -p ControlGroup --value)
```

```
unit cgroup: /user.slice/user-1000.slice/user@1000.service/app.slice/t019-probe.scope
  cgroup.procs  mode=-rw-r--r--     <- writable by the owning user
  cgroup.freeze mode=-rw-r--r--
  cgroup.kill   mode=--w-------
  memory.max    mode=-rw-r--r--

outside pid 96990 in cgroup: .../app-ai.opencode.desktop-5774.scope
move: ok
now: 0::.../t019-probe.scope

freeze ok; moved pid state=S
thawed state=S
```

Both the move and the freeze were accepted. Note that `cgroup.freeze` does not
change what `/proc/<pid>/stat` reports — the task stays in state `S` while it is
not scheduled — so freeze must be verified by observing non-progress, not by
reading process state. T-009 already established that freeze stops progress for
a member of the scope; this probe establishes that a process started elsewhere
can be made a member.

## Conclusions

1. **We are not limited to the first command.** Any command we start can be
   placed in the sandbox's cgroup, because the join is performed by a process we
   control: write the child pid to `cgroup.procs` before `exec`, or start the
   join inside the scope. Limits then apply from that moment, which is before
   the command has allocated anything.
1. **Pause does not need cgroups at all.** Enumerating `/proc` by pid-namespace
   inode and signalling the members gives a complete, unescapable pause and
   resume, and it works on hosts with no systemd and no delegation. This is a
   strict improvement on the lifecycle ADR's process-group fallback, which
   missed `setsid` escapees.
1. **`cgroup.kill` is the right teardown.** It is write-only, atomic and
   available on this host: one write kills every member of the scope, with no
   pid enumeration and no race.
1. **The two mechanisms answer different questions.** Namespace enumeration is
   the reliable one for pause/resume and for finding members; cgroups are the
   only one that can bound memory and task count, and the only one that can
   freeze atomically rather than one signal at a time.

## Caveats

- **Freeze and limits are not a security boundary here.** Delegation gives the
  user's own processes write access to the scope's `cgroup.procs`, so a hostile
  workload running as the same uid can move itself out of the scope. Docker does
  not have this problem because the container user cannot write its own cgroup.
  Treat cgroup controls as resource management for cooperative workloads, and
  pid-namespace enumeration as the mechanism that holds under a hostile one.
- Assigning a pid at fork time was not exercised end to end; the probe moved a
  process that was already running. The production join should write the child
  pid before `exec` so the window is empty.
- Nested cgroups were not tested: a joined process that creates its own subtree
  under the scope still counts against `memory.max` for the parent, but
  `cgroup.kill` on the parent covers it, and freeze does not propagate upward.
