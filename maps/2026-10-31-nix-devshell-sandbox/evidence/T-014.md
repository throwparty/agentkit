# T-014: where must the egress proxy sit?

**Question.** Where must an egress proxy sit to be reachable from a bwrap
sandbox, given the sandbox has its own network namespace?

**Method.** A unix-socket listener on the host, bind-mounted into the holder at
`/run/proxy.sock`, and a check from a joined process for both transports:

```
=== T-014: is the host's TCP loopback reachable from the sandbox?
  host loopback: Connection refused

=== T-014: is the bind-mounted host unix socket reachable?
  unix socket reply: proxied
```

**Observation.** The unshared network namespace has its own loopback with nothing
listening, so a host service on `127.0.0.1` is unreachable. A unix socket is not
part of the network namespace: it is a file, and a bind mount puts it in the
sandbox's view. Connecting to it is an ordinary filesystem operation, so it
reaches the host process.

**Conclusion.** **Outside the sandbox, reached through a bind-mounted unix
socket.** The proxy runs on the host as an ordinary process, and the sandbox gets
one socket path in its view. That is strictly better than the alternatives:

- **A proxy inside the holder's network namespace** would work — a joined
  command already reaches `127.0.0.1` inside the namespace (T-013) — but it puts
  a network-facing process inside the confinement, has to be started and
  supervised per sandbox, and dies with the holder.
- **A TCP proxy on the host** is unreachable, as observed.

What the unix socket placement buys:

- One long-lived proxy can serve every sandbox, and outlive any one of them.
- The sandbox never needs a network namespace with a route, only loopback for
  local servers, which is what it already has.
- The proxy's policy is enforced on the host, outside the workload's reach, so a
  workload cannot reconfigure it by writing to its own view.
- `HTTP_PROXY`-style variables are optional: a workload that needs a specific
  socket path gets it, and one that does not need the network gets no socket at
  all.

Constraints to carry into the design:

- The socket path must be created before the holder starts, and the holder's
  bind list must include it. That makes it part of the sandbox's typed view, not
  an afterthought.
- The socket is a writable object from the sandbox's perspective (it can connect,
  and can hold the connection open). The proxy must treat every connection as
  hostile: no ambient credentials, no host filesystem access, and a bounded
  number of connections.
- It grants egress only to what the proxy allows, so the `NetworkEgress` facet
  is really "is a proxy socket present in the view", not "does the sandbox have a
  route".
