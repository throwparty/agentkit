# T-023: does the implemented contract carry the store closure?

**Question.** Does the provider contract, as implemented at
`litterbox-sandbox-provider-contract`, carry the devShell's Nix closure to the
backend that must bind it, or must the backend derive it?

**Method.** Reading the implemented contract and the one call site that builds a
create request.

## Observation

`crates/agentkit-litterbox/src/sandbox/contract.rs`:

- `Workspace` (lines 30-34) carries a single `source: PathBuf`.
- `EnvironmentSource` (lines 71-82) is either `Mechanism` or
  `Captured { from: String, variables: Vec<(String, String)> }`.
- `CreateRequest` (lines 85-101) is name, project slug, workspace, environment,
  forward bind, setup command and ports. There is no field for store paths.

`crates/agentkit-litterbox/src/orchestrator/service.rs:154`:

```rust
environment: crate::sandbox::contract::EnvironmentSource::Mechanism,
```

So the closure T-022 derived (`ENV=$(nix print-dev-env ./nix --json | jq -r
'.variables.out.value'); nix path-info -r "$ENV"` → 238 paths) has nowhere to
cross the contract as written.

## Conclusion

No. The contract carries environment variables and a workspace source, not the
store closure. Two consequences:

- The bwrap backend can still be built against what exists by binding all of
  `/nix/store` read-only, which T-004 and T-016 proved sufficient.
- The closure-derived bind set (T-022) needs either a new `CreateRequest` field
  or a richer `EnvironmentSource`; that is a contract amendment decided in
  `nix-devshell-env-capture`, not a spike.

The second is a choice about where the closure lives, not an unknown about
whether it can be obtained: the capture procedure already produces it.
