# T-023: does the implemented contract carry the store closure?

**Question.** Does the provider contract, as implemented at
`litterbox-sandbox-provider-contract`, carry the devShell's Nix closure to the
backend that must bind it, or must the backend derive it?

**Method.** Reading the implemented contract and the one call site that builds a
create request.

## Observation

`crates/agentkit-litterbox/src/sandbox/contract.rs`:

- `Workspace` (lines 30-34) carries a single `source: PathBuf`.
- `EnvironmentSource` (lines 71-82) is either `Mechanism` or
  `Captured { from: String, variables: Vec<(String, String)> }`.
- `CreateRequest` (lines 85-101) is name, project slug, workspace, environment,
  forward bind, setup command and ports. There is no field for store paths.

`crates/agentkit-litterbox/src/orchestrator/service.rs:154`:

```rust
environment: crate::sandbox::contract::EnvironmentSource::Mechanism,
```

So the closure T-022 derived (`ENV=$(nix print-dev-env ./nix --json | jq -r
'.variables.out.value'); nix path-info -r "$ENV"` → 238 paths) has nowhere to
cross the contract as written.

## Conclusion

No. The contract carries environment variables and a workspace source, not the
store closure. Two consequences:

- The bwrap backend can still be built against what exists by binding all of
  `/nix/store` read-only, which T-004 and T-016 proved sufficient.
- The closure-derived bind set (T-022) needs either a new `CreateRequest` field
  or a richer `EnvironmentSource`; that is a contract amendment decided in
  `nix-devshell-env-capture`, not a spike.

The second is a choice about where the closure lives, not an unknown about
whether it can be obtained: the capture procedure already produces it.

## Re-answer, after `devshell-environment-implementation` (H)

H amended the contract, so the observation above no longer holds. Re-read at
commit `dfcbd6e8`:

- `Contributions` (`contract.rs:169-180`) carries `mounts: Vec<PathBuf>`,
  documented as "Absolute read-only paths to mount".
- `ResolvedStep` (`contract.rs:224-235`) carries `contributions: Contributions`
  beside `identity`, `kind`, `placement` and `sandbox`.
- `CreateRequest.provision` (`contract.rs:258-259`) is `Vec<ResolvedStep>`, so
  the resolved contributions cross the request. There is no separate store-path
  field and none is needed.
- `prepare::devshell` fills the field:
  `contributions.mounts = super::closure::closure(output_path, ctx.store_view,
  ctx.runner)` (`prepare/devshell.rs:85`).
- `closure()` (`prepare/closure.rs:10-48`) runs `nix path-info -r` on the
  devShell output path, sorts and deduplicates it, and returns the path list
  for `StoreView::Closure` or `/nix/store` alone for `StoreView::Whole`.
- The `devshell` kind reports `ContributionSort::Mount` in its description
  (`provision/kind/devshell.rs:18`), so the resolver accepts a backend that
  renders mounts and reports one that does not.

The ignored host test `this_repository_captures_and_closes_over_the_devshell`
(`prepare/mod.rs:280-314`) asserts on this checkout that the prepared
contributions contain `CARGO_HOME`, that the mount list is non-empty, and that
no mount path ends in `bin/nix`.

**Revised conclusion.** Yes, since H. The backend receives the derived closure
on the request and renders it; binding all of `/nix/store` remains available as
`StoreView::Whole` rather than through a different field. What C and D still
own is rendering the list into bwrap arguments and an SBPL profile
respectively, and validating the mount limit for a large closure. Nothing about
obtaining or carrying the closure remains open.
