# T-049. Is fork+apply safe in a threaded process?

Answer: it did not fail here, 400 of 400, but that does not license it.
Applying a profile in a forked child of a four-thread process succeeded from
both main and a worker thread with no hangs or crashes, and the exec'd-helper
control behaved identically. The separate helper remains required for a
different reason: the profile is a property of the process, so applying it
inside the server would confine the server, not just the command.

Host: macOS 27.2.1 (26B131), arm64. Probed 2026-11-14.

## Reproduce

```
cc -O1 -o build/forktest T-049-forktest.c
./forktest denywrite
./forktest 200
```

Four threads spin on a mutex and malloc. The child applies
`(version 1)(deny default)` and `_exit(0)`. The parent waits with a 5 s
deadline; a timeout kills the child and counts a hang.

## Results

```
threads=4 iterations=200
fork_from_main ok=200 failed=0 hung=0 crashed=0 worst_ms=11.0
fork_from_worker ok=200 failed=0 hung=0 crashed=0 worst_ms=13.3
spawn_helper ok=200 failed=0 hung=0 crashed=0 worst_ms=13.5
counter=232049567
```

No failure of any kind, and no observable cost difference between fork+apply
and spawning a helper.

The per-process scope is visible separately:

```
$ ./forktest denywrite
exit=0
```

The child applied a deny-default profile, failed to open
`/tmp/t049-write` with `EPERM`, and exited 0. A parent applying that profile
would deny itself the same write. The sandbox cannot be scoped to a child that
does not exec.

## Why the helper is still mandated

- POSIX permits only async-signal-safe calls between `fork` and `exec`.
  `sandbox_init` is not one. Zero failures in 400 runs is evidence, not a
  guarantee; a deadlock in a rarely-taken path would wedge the server, and the
  test cannot enumerate Xcode's or the kernel's locks.
- The intended boundary is exec: the helper applies the profile and becomes the
  command. That is what confines the workload without confining litterbox.
- The control shows the helper path is not slower, so there is no performance
  argument for the risky one.

## Consequence for D

- Always spawn a helper process that applies the profile and execs. Never call
  `sandbox_init` in the server, and never rely on `pre_exec` after a threaded
  fork.
- Readiness (T-048) uses the same helper with a probe profile, so there is one
  apply path to audit.
- Record the measured result as a note, not as permission: a future macOS could
  change the lock behaviour, and the helper approach is invariant to that.
