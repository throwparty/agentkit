# T-034: does a killed client leave a zombie inside the sandbox?

**Question.** When the client that joined a command is killed while the command
still runs, does the sandbox accumulate a defunct process for the rest of its
life, or does the process get reaped?

**Method.** Start a holder as in T-033 and wait until the view is usable. Join a
client with `nsenter -t <pid> -U -i -n -p -m -u --preserve-credentials
-r/proc/<pid>/root -- sh -c 'sleep 2'`, then `kill -9` the client 0.3s later,
while the `sleep` still runs. Read the process table inside the sandbox at 0.5s
and at 4.5s, and count processes in state `Z`.

Reproduce with `evidence/T-033-039-probes.sh`.

**Observation.**

```
process table 0.5s after the client died:
    PID    PPID STAT COMMAND
      1       0 S    bwrap
      2       1 S    sleep
      6       0 S    sleep
      7       0 R    ps

process table 4.5s after the client died:
    PID    PPID STAT COMMAND
      1       0 S    bwrap
      2       1 S    sleep
      8       0 R    ps

defunct processes: 0
```

The orphaned command shows `PPID 0`, which means its parent is outside the
sandbox's pid namespace, and it is gone by 4.5s with no defunct entry left
behind. T-013 recorded the same `PPID 0` and left accumulation unmeasured; this
probe measures it.

**Conclusion.** No zombie survives. The command is reparented outside the pid
namespace and reaped there, so the sandbox does not accumulate unreaped
processes when a client dies. The pid-1 process is still what kills the
namespace on delete. Reaping is therefore not a reason to reject a `sleep`
holder, and `--as-pid-1` is not needed.
