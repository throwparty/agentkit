# T-028: what does a backend report?

**Question.** Should a backend report support per kind, or support for the
contributions it applies, and is that report static or derived from readiness?

**Method.** Read the prototype findings against the implemented contract and
the Docker backend.

## Observation

`adrs/2026-11-07-devshell-environment/findings.md:46-61` separates two
questions that had been one. The host asks whether a step can be prepared here,
which is readiness and depends on the kind. The sandbox asks whether the
contributions can be applied, which is an environment and a list of read-only
mounts. The prototype's launch path never learned the kind, and its requirement
refusal checked the view rather than the step.

The contract already splits the two reports:

- `crates/agentkit-litterbox/src/sandbox/contract.rs:480` declares
  `Backend::readiness`, which is asynchronous and host-specific.
- `crates/agentkit-litterbox/src/sandbox/contract.rs:489` declares
  `Backend::provision_support`, which is synchronous because it is a property
  of the mechanism.
- `ProvisionSupport` at `contract.rs:98-115` carries `kind`, `state`, `reason`,
  `remedy` and `fallback`.
- `crates/agentkit-litterbox/src/backends/docker/backend.rs:720` returns the
  static list.

`maps/2026-10-31-nix-devshell-sandbox/HANDOVER.md:163-164` states the same rule
for the provider contract: provisioning support is static, and host readiness
stays in `Backend::readiness`.

## Conclusion

A static declaration of the contribution sorts a backend can apply. Today that
is an environment and read-only mounts. Whether a mount can actually be made
depends on the host, so a failure there is a readiness failure or a create-time
refusal with the backend's own limit, not a change to the static report. No
backend needs to know a kind once preparation is host-side, so `ProvisionSupport`
is keyed by contribution sort rather than by `ProvisionKind`.
