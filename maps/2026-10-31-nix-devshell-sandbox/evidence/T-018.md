# T-018: can a sandboxed command invoke nix?

**Question.** Can a bwrap-confined command run `nix` at all, and what does
granting that cost?

**Method.** The T-016 holder, first as built, then with `/nix/var/nix` bound in
so the daemon socket is visible.

**Observation.**

```
=== nix binary reachable and version
  nix (Nix) 2.34.9

=== is there a daemon socket in the view?
  ls: cannot access '/nix/var/nix/daemon-socket': No such file or directory

=== nix eval
  warning: /nix/var/nix does not exist, so Nix will use
           "/home/lukecarrier/.local/share/nix/root" as a chroot store
  error: unable to download 'https://channels.nixos.org/flake-registry.json':
         Could not resolve host: channels.nixos.org

=== nix develop of this repo
  error: Failed to open archive (Source threw exception: error: unable to
         download 'https://github.com/numtide/flake-utils/archive/
         11707dc2f618dd54ca8739b309ec4fc024de578b.tar.gz':
         Could not resolve host: github.com)
```

With `/nix/var/nix` bound read-write the socket appears in the view
(`srw-rw-rw- root root`, shown as `nobody nogroup` through the uid map) and the
daemon answers:

```
=== T-018: can the sandbox write a path into the host store via the daemon?
  added: /nix/store/dcabh7zdzcdk2ljfrj654byn29p824rp-plant.txt
  host sees it: -r--r--r-- 1 root root 31 Jan  1  1970 .../plant.txt
```

`nix build` still failed because evaluation needs the flake registry and the
nixpkgs source, and the sandbox has no network and a cold eval cache.

**Conclusion.** `nix` executes — the binary is in the view through the system
profile — but it is useless without two grants that must not be made:

1. **The daemon socket.** With it, a sandboxed command added
   `/nix/store/dcabh7zdzcdk2ljfrj654byn29p824rp-plant.txt` to the *host* store,
   root-owned, and the host can execute it. The demonstrated authority is
   **growth of the host store and build requests that run outside this
   sandbox**, under the daemon's own user and sandbox — not mutation of an
   existing immutable path, which no probe attempted and which content
   addressing makes hard. T-004 already names the daemon as an explicit write
   channel beside a private store, so this does not contradict it; it puts a
   number on what that channel buys a confined workload. The policy conclusion
   is unchanged: withhold the socket.
1. **Network.** Anything not already realised needs the registry and the input
   tarballs. The eval cache lives in the user's home, which a sandbox home is
   not.

So the answer is: **yes it can, and we should not let it.** The environment is
captured on the host (T-011) and applied at exec (T-016), and `nix` stays outside
the sandbox. Projects that need `nix` at build time — flake-aware build scripts,
`nix shell` wrappers — are out of scope for this provider and fail with their own
error, which is a legible outcome rather than a silent one.

Carried note: the daemon probe `nix build` also showed the daemon binding a
chroot store under `$HOME/.local/share/nix/root` when `/nix/var` is absent. That
path is inside the sandbox home, so without the socket nix degrades into
writing a private store that evaluates nothing. Not useful, but not dangerous.
