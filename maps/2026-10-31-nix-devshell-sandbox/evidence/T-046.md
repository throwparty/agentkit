# T-046. Is the developer directory platform baseline or toolchain contribution?

Answer: a toolchain contribution, discovered at runtime. It is not a
platform constant and not a single path. The grant unit is the Xcode
installation root, not `xcode-select -p`'s `Developer` directory, and it comes
with host state (the Xcode licence plist) and the user temp directory.
On this host `xcode-select -p` returns `/Applications/Xcode.app/Contents/Developer`,
and `/Library/Developer/CommandLineTools` also exists, so the selection is host
state rather than a fixed location. Hardcoding either is the Nix/macOS
conflation this ticket rules out.

Host: macOS 27.2.1 (26B131), arm64. Probed 2026-11-14.

## Reproduce

`T-043-helper.c` with a `--without-developer` switch that omits
`/Library/Developer` and `/Applications/Xcode.app/Contents/Developer` from the
platform baseline. The workload is:

```c
#include <stdio.h>
int main(void){printf("built\n");return 0;}
```

```
cc -o hello hello.c
```

## Results

| Profile | Result |
|---|---|
| no developer path | `xcrun: error: unable to load libxcrun ... libxcrun.dylib (file system sandbox blocked open())` |
| `Contents/Developer` only | `dyld: Library not loaded ... Contents/SharedFrameworks/DVTSystemPrerequisites.framework ... blocked open()` then `unable to locate xcodebuild` |
| `Contents/Developer` as `--read` (same) | identical failure |
| `Xcode.app` root + `--write $DARWIN_USER_TEMP_DIR` | reaches the licence check: `You have not agreed to the Xcode license agreements` |
| `Xcode.app` root + `/Library/Preferences` read + user temp write | builds; `./hello-d` prints `built` |

So the developer directory is neither sufficient nor the right unit. The
installation root is the right unit.

## What is actually required

- The Xcode **installation root** (`/Applications/Xcode.app` here), not
  `xcode-select -p`'s `Contents/Developer`. `clang` reaches siblings of
  `Developer`, notably `Contents/SharedFrameworks`.
- The host state that records licence acceptance
  (`/Library/Preferences/com.apple.dt.Xcode.plist`, root-owned, present here).
- A writable per-user temp directory. `xcrun` writes its cache to
  `confstr(_CS_DARWIN_USER_TEMP_DIR)` (`/var/folders/.../T`) even when `TMPDIR`
  is set into the workspace, and reports
  `couldn't open cache file ... (Operation not permitted)`.

That last point matters beyond this ticket: a C toolchain probes a host temp
directory that the workspace variables do not control. The build completed
despite the cache warnings, but the backend cannot claim "no writes outside the
workspace" for a compiler workload without either granting that directory or
proving the warnings are always benign.

## Consequence for D

- Do not put any developer path in the static baseline. Resolve it at readiness
  or create time from `xcode-select -p`, then widen to the installation root,
  and supply it as a read grant alongside the step contributions. It is
  optional: a sandbox with no compiler needs none of it.
- The discovered path may be `/Applications`, `/Library/Developer/CommandLineTools`
  or a `/nix/store` path. The backend never assumes which, and never emits a
  store grant because the host happens to be Nix-configured.
- Granting the host temp directory is a separate decision, because it weakens
  the "writes stay in the workspace" invariant. It belongs in the ADR as an
  explicit exception with a scope, not as a silent baseline entry.

## Caveats

- This is one Xcode installation (27.2) on one host. A CommandLineTools-only
  selection may need a different set; the discovery step, not the path list, is
  the durable finding.
- Licence state is host policy. A CI machine that has accepted the licence
  differs from a fresh one; readiness should report it, not paper over it.
