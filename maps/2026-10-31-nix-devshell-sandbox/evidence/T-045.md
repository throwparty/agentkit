# T-045. Cross-process lifecycle from a recorded process group

Answer: yes. A later, unrelated process can stop, continue and kill a
sandbox by signalling the recorded process group; the launcher need not survive.
A child that calls `setsid` leaves the group and survives the group kill, stays
confined, and can no longer be addressed by the group.

Host: macOS 27.2.1 (26B131), arm64. Probed 2026-11-14.

## Reproduce

`T-045-launcher.c` forks, calls `setsid` in the child, applies a profile, execs the
command, writes the child pid to a state file and exits. The recorded pid is the
session and group leader. `T-045-probe.sh` drives it and builds into
`evidence/build/`.

```
bash T-045-probe.sh
```

Command: `/bin/sh -c 'i=0; while :; do echo $i >> <ws>/progress; i=$((i+1)); /bin/sleep 0.05; done'`

## Results

```
launcher: child pid/pgid=90640
recorded pgid=90640
progress after start: 16 bytes
kill -STOP exit=0
size a=16 b=16; unchanged=yes
kill -CONT exit=0
size c=41; grew=yes
kill -KILL exit=0
size d=41 e=41; stopped=yes
group alive after kill: no
```

The group leader was reparented to pid 1 when the launcher exited
(`90640 1 90640`), and the later process still addressed it. `kill(-pgid, 0)`
returned non-zero after the kill, so liveness is observable without a
supervisor.

## The setsid escapee

```
recorded pgid=90784
escapee pid=90787
kill -KILL group exit=0
escapee alive after group kill: yes
escapee ps: 90787 1 90787 0 <ws>/escapee <ws>/escape /tmp/t045-escape-outside <ws>/escape.pid
escape file bytes: 4
out-of-workspace file present: no
```

The escapee has its own group (90787) and session, so the group kill misses it.
It keeps writing inside the workspace and its attempt to write
`/tmp/t045-escape-outside` is denied: confinement is inherited and cannot be
dropped. It is only unaddressable by group.

## Consequences for D

- `SandboxStatus::Paused` maps to `SIGSTOP` on the recorded group;
  resume to `SIGCONT`; delete to `SIGKILL` on the group followed by workspace
  reclamation.
- The record must carry the group leader pid. A pid alone is reusable, so a
  start-time or a sentinel check is needed before signalling; this probe did not
  exercise reuse and the ADR should not assume a bare pid is safe.
- macOS has no `setsid(1)`. A program that calls `setsid(2)` is the only way to
  demonstrate the escape; production should document it rather than try to close
  it, because there is no pid namespace.
- The escapee stays confined, so the risk is unaddressable compute, not an
  isolation break.

## Caveats

- The first scenario's writer is a shell loop; `sleep` resolves through the
  caller's `PATH`. The probe uses `/bin/sleep` explicitly so the sandbox does
  not need a Nix grant.
- Signals cross the sandbox because the sandbox is a profile, not a namespace;
  a same-uid process outside can always signal it.
