# T-022: can the bind set come from the Nix closure?

**Question.** Can the store bind set be derived from the devShell's Nix closure,
instead of binding all of `/nix/store` or discovering paths by failure?

**Method.** The closure of the devShell environment itself:

```bash
ENV=$(nix print-dev-env ./nix --json | jq -r '.variables.out.value')
nix path-info -r "$ENV" > closure.txt        # 238 paths
```

Then a holder that binds **only** those paths — one `--ro-bind` per path, passed
NUL-separated through `bwrap --args` — plus `/proc`, `/dev`, a tmpfs `/tmp`,
`/etc`, and the workspace at its host path (T-016). The captured allowlist from
T-011 is handed to `bwrap` with `--setenv`, so no helper binary is needed
inside. The workload is `cargo test -p agentkit-path`.

**Observation.**

```
closure: 238 paths
  coreutils:   /nix/store/61685…-coreutils-9.11
  bash:        /nix/store/axl12…-bash-5.3p9
  rust:        /nix/store/262w9…-rust-default-1.98.1
  gcc wrapper: /nix/store/hbsz2…-gcc-wrapper-15.2.0
  glibc:       /nix/store/rkiwr…-glibc-2.42-84

=== store view: is /nix/store a full tree or just the closure?
  entries visible: 238 (closure has 238)

=== cargo test with only the closure bound
test result: ok. 5 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
  exit: 0
```

For scale: the host store holds **57,534 paths**. The closure is **238**, about
0.4%, totalling 5.44 GiB.

**Conclusion.** Yes. The closure of the devShell environment is a sufficient bind
set, it is derived rather than maintained, and it narrows the store view by two
orders of magnitude.

What that buys:

- **No by-failure attribution.** The Linux spike's baseline was "discovered by
  failure" and its own findings call the list host-specific. The closure tracks
  the devShell: change the flake, and the bind set changes with it, with no
  human step.
- **The dyld class of bug disappears.** The macOS spike hit a sibling store path
  the hand-written read baseline had missed. A closure cannot miss a path Nix
  recorded as a runtime dependency, because that is what a closure is.
- **Less is reachable.** A workload that can see 238 store paths has far less to
  abuse than one that can see 57,534, and T-004's "the store is not confidential"
  assumption stops doing so much work.

Limits recorded:

- **238 is derived, not minimal.** It includes the Rust standard libraries for
  Windows and Apple targets, pulled in by `rust-overlay`'s target list, which this
  workload never touches. A narrower bind set is possible; the point is that this
  one required no judgement.
- **Individual binds are O(n) mounts.** 238 is comfortable and needs `--args` to
  stay inside the argument limit. A devShell of several thousand paths would make
  setup cost measurable; T-003 measured bwrap setup at ~20 ms with a handful of
  mounts.
- **Runtime-discovered dependencies are still the limit**, exactly as on the host:
  a `dlopen` of a library the derivation never declared fails. That is the same
  contract `nix run` offers, and it fails legibly rather than opening the store.
- **Not tested on macOS.** The equivalent is the closure as a set of `file-read*`
  grants; the closure computation is host-side and identical, but the profile
  rendering is a Darwin task (T-017).
- **[jail.nix](https://sr.ht/~alexdavid/jail.nix/) is prior art** for this idea
  and for the combinator vocabulary; its combinators (`network`, `gui`, `gpu`,
  `readonly`, `rw-bind`) map onto the facets. It wraps derivations rather than
  devShells, so it does not solve the environment capture or the holder.
