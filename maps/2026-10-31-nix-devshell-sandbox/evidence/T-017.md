# T-017: does a host-captured devShell environment build inside the macOS sandbox?

**Question.** Can a devShell environment captured on the host produce a working
build inside the macOS sandbox, and which baseline additions does the closure
need?

**Method.** Capture, sanitise, build, then attribute the denials.

```bash
nix develop ./nix --command sh -c 'nix print-dev-env ./nix --json > /private/tmp/lbx-devenv.json'
# 94 exported variables with values, 107 bash functions on this host
# write the exported ones as `export NAME='value'` to devenv.sh

mkdir -p /private/tmp/lbx-t017/{ws,home,ws/tmp}
cp -R adrs/2026-10-31-darwin-app-sandbox/poc/fixture /private/tmp/lbx-t017/ws/fixture
cp /private/tmp/lbx-devenv.sh /private/tmp/lbx-t017/ws/

sandbox-custom --tag t017 --workspace /private/tmp/lbx-t017/ws -- \
  /bin/sh -c '. ./devenv.sh && export HOME=/private/tmp/lbx-t017/ws/home \
    TMPDIR=/private/tmp/lbx-t017/ws/tmp TMP=/private/tmp/lbx-t017/ws/tmp \
    TEMP=/private/tmp/lbx-t017/ws/tmp NIX_BUILD_TOP=/private/tmp/lbx-t017/ws/tmp \
    && cd fixture && cargo build && cargo test'
```

**Observation.** The first attempt failed in the linker, twice, and both are
environment problems rather than sandbox problems:

1. Unmodified, the capture carries the build sandbox's scratch paths:
   `TMPDIR`, `TMP` and `TEMP` point at `/nix/var/nix/builds/nix-<id>`, and
   `HOME` is `/homeless-shelter`. The cc wrapper then fails with
   `mktemp: failed to create file via template '/nix/var/nix/builds/…/cc-params.XXXXXX'`.
1. Unsetting `NIX_BUILD_TOP` is worse: the clang wrapper reads it unguarded and
   dies with `NIX_BUILD_TOP: unbound variable`.

Repointing those five variables into the workspace fixes both. `cargo build` and
`cargo test` then complete: `Finished dev profile` and a passing test run.

Denials during the successful run: **524**, every one tolerated.

| Operation | Target | Count | Effect |
|---|---|---|---|
| `file-read-metadata` | `/nix` | 166 | `/nix` is a symlink to `/nix/store`; the store itself is granted |
| `file-read-metadata` | `/System/Cryptexes/OS`, `/System/Cryptexes/Rosetta` | 120 | Apple silicon cryptex aliases |
| `system-info` | `vfs.disk-space` | 45 | toolchain disk-space probe |
| `file-write-data` | `/dev/dtracehelper` | 41 | toolchain probe |
| `file-read-metadata` | `/var`, `/etc` | 56 | firmlink aliases of `/private/var`, `/private/etc` |
| `file-read-data` | `…/Cryptexes/OS/System/Library/dyld` | 40 | dyld falls back to the in-memory cache |
| `ipc-posix-shm-read-data` | `apple.shm.notification_center` | 15 | notification centre |
| `file-write-data` | `/dev/tty` | 9 | no controlling terminal attached |

**Conclusion.** Yes. A host-captured devShell environment produces a working
build and test run inside the macOS sandbox, and **no baseline addition was
required**: every denial above is tolerated by the toolchain, and the profile
already grants the store, the developer directory and the ancestors its metadata
rule needs.

The work is in the environment, not the profile: the capture must be sanitised
of build-sandbox scratch variables (`HOME`, `TMPDIR`, `TMP`, `TEMP`,
`NIX_BUILD_TOP`) and those repointed into the workspace, and `NIX_BUILD_TOP` must
remain set because the clang wrapper reads it unguarded.

This mirrors T-016 on Linux, where the same capture builds inside the holder.
The difference is that Linux needed an allowlist derived from the capture and a
private home; here the helper's fixed environment allowlist is replaced wholesale
by the captured one, which is what the `env` escaping above demonstrates.

**Limits.**

- The capture used `print-dev-env` exports only, without the differential
  overrides T-011 requires. The four variables the shellHook adds
  (`CARGO_HOME`, `RUSTUP_HOME`, `RUSTFLAGS`, `NIX_GCROOT`) and its `PATH`
  prepend were therefore absent, and this workload did not need them: the base
  `PATH` already reaches the Nix toolchain directly. A project whose hook sets
  flags the toolchain reads must apply T-011's differential; the Darwin result
  would be unchanged in kind, not in detail.
- Repointing `NIX_BUILD_TOP` rather than unsetting it is load-bearing and
  fragile: it works because the clang wrapper reads the variable unguarded, so
  the value matters less than its presence. A wrapper that *requires* the
  `/nix/var/nix/builds` shape would need a different answer.
- The profile grants store reads by path rule over the whole store, so the
  T-022 narrowing has not been applied here. Doing so means emitting one
  `file-read*` rule per closure path instead of one for `/nix/store`, which is
  a Darwin-side task (step 4), not an open question.
