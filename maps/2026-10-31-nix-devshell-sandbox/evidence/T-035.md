# T-035: a closure larger than 238 paths

**Question.** Does a sandbox start and run a command when the bind list is much
larger than the 238 paths T-022 measured, and how many mounts does bwrap
create?

**Method.** Take the system closure, which is larger than a devShell closure and
already in the store, and bind each path individually at its own absolute path,
exactly as a renderer would.

```
mapfile -t C < <(nix path-info -r /run/current-system | sort -u)
for p in "${C[@]}"; do args+=(--ro-bind "$p" "$p"); done
```

Start a holder with those arguments, wait until the view is built, count the
mount table and run a command inside. Reproduce with
`evidence/T-033-039-probes.sh`.

**Observation.**

```
closure paths: 1779
status document after: 43ms
view usable after: 4246ms
holder alive: yes
mountinfo lines: 1801
store mounts: 1779
command inside: ok
```

**Conclusion.** Yes. 1779 individual binds produce a usable sandbox and run a
command. bwrap does not merge adjacent binds: the mount table holds one entry
for each path, 1779 store entries in a table of 1801.

An earlier reading of this probe saw 52 mount entries and concluded that bwrap
merged adjacent binds. That reading was taken 300ms after the status document,
before setup had finished, when only part of the view was mounted. The
correction is recorded here because the difference decides how a backend checks
the view, and because it is the same mistake that T-039 measures directly.

The cost is setup time, not a count: 4.2s for 1779 binds against 60ms for a
three-bind view. The prototype's 238 paths is not a ceiling, but a large closure
delays every create.
