# T-013: joining a live bwrap sandbox

**Question.** Can an unprivileged process join a live bwrap sandbox, so
successive commands share pid and network context without a supervisor of our
own?

**Method.** Two sources.

1. `flatpak-builtins-enter.c` (Flatpak 1.18.4, `app/`), as prior art for the
   technique, and `man flatpak-enter`.
1. A probe on NixOS, kernel 7.2.14, bubblewrap 0.12.0, as an unprivileged user.

## Prior art: what `flatpak enter` actually does

`flatpak enter` does **not** start a second sandbox. It opens
`/proc/<pid>/ns/{user,ipc,net,pid,mnt}` for the running instance's child pid and
calls `setns()` on each, in the order `user_base`, `ipc`, `net`, `pid`, `mnt`,
`user`, skipping any namespace whose inode already matches the caller's. It then
`chroot`s to `/proc/<pid>/root`, `chdir`s to the recorded cwd, `setgid`/`setuid`s
to the sandbox owner, and calls `drop_all_caps()`.

The environment is not derived: it is copied from `/proc/<pid>/environ`, minus
`PULSE_*`, `XDG_RUNTIME_DIR`, `DBUS_*`, then `XDG_RUNTIME_DIR` and the dbus and
pulse addresses are re-added for the caller.

The man page and the source agree on the privilege model: it works "as a regular
user if the system support unprivileged user namespace", and the EACCES on
`/proc/<pid>/root` and EPERM on `setns` both produce "entering not supported
(need unprivileged user namespaces, or sudo -E)".

So the answer to the question as posed about Flatpak: **the same namespaces**,
by setns, not a fresh sandbox over the same ostree tree. Flatpak's `run --command=…` is the other thing — a new sandbox — and `enter` is the Kubernetes
pause-container shape.

## Probe

```bash
BWRAP=$(nix build --no-link --print-out-paths nixpkgs#bubblewrap)/bin/bwrap
ROOT=$(mktemp -d); STATUS=$(mktemp)

"$BWRAP" \
  --unshare-user --unshare-pid --unshare-ipc --unshare-uts --unshare-cgroup --unshare-net \
  --disable-userns --die-with-parent \
  --clearenv --setenv PATH /run/current-system/sw/bin \
  --hostname litterbox \
  --ro-bind /nix/store /nix/store \
  --ro-bind /run/current-system /run/current-system \
  --ro-bind /etc /etc \
  --proc /proc --dev /dev --tmpfs /tmp \
  --dir /src --bind "$ROOT" /src --chdir /src \
  --json-status-fd 3 \
  -- sleep infinity 3>"$STATUS" &
OUTER=$!
# wait for the status document, then
PID=$(grep -o '"child-pid": [0-9]*' "$STATUS" | grep -o '[0-9]*')
enter() { nsenter -t "$PID" -U -i -n -p -m -u --preserve-credentials \
            -r"/proc/$PID/root" -W/src -- "$@"; }
```

## What the probe established

1. **Joining works unprivileged.** Same uid, no sudo, no capabilities beyond
   what the namespace owner already has. `--disable-userns` does not prevent it:
   that flag stops *creating* a further user namespace from inside, not
   `setns` from outside.
1. **The addressable pid comes from bwrap, not from the caller.** The process the
   caller spawns (`$!`) stays in the host's namespaces; bwrap forks the sandbox
   and reports it as `child-pid` on `--json-status-fd` (or `--info-fd`). Targeting
   `$!` fails with `cannot open /proc/<pid>/root`. The production argv already
   emits `--json-status-fd`, so the plumbing exists.
1. **`setgroups` is denied in bwrap's user namespace**, so `nsenter` fails with
   `setgroups failed: Operation not permitted` unless given
   `--preserve-credentials`.
1. **`--wd` resolves in the outer namespace** and fails; `--wdns` (`-W`) is the
   working equivalent. `--root`/`-r` is fine.
1. **Cross-command loopback works and stays isolated.** Two joined processes
   share the sandbox's netns; the host cannot reach the listener.
1. **The `setsid` escape is closed.** A joined process that calls `setsid` still
   lives in the sandbox's pid namespace, and when pid 1 of that namespace exits
   the kernel kills every member. SIGKILL to the holder reaped the escapee that
   the process-group design could not.

## Design consequences

- The sandbox is a **holder**: `bwrap … -- sleep infinity`, exactly the pause
  container. Every command is a join. The workspace is still the shared
  filesystem contract, and now pid and net are shared too.
- `pause` and `resume` regain their sandbox-level meaning: freeze the holder's
  cgroup scope, or `SIGSTOP` the holder when there is no user manager. This is
  stronger than the lifecycle ADR's per-command model and no longer vacuous
  when nothing is running.
- `delete` becomes "kill the holder", which by pid-namespace death kills every
  descendant including `setsid` escapees.
- The join should be implemented in-process, as Flatpak does, not by spawning
  `nsenter`: setns in the documented order, `chroot` to `/proc/<pid>/root`,
  `chdir`, drop credentials, `capset` to zero, `exec`. `nsenter` needs
  `--preserve-credentials` and `--wdns` to compensate for its own defaults, and
  it does not drop capabilities.
- `--die-with-parent` on the holder ties the sandbox to the CLI's lifetime,
  which the Docker backend does not do. Drop it on the holder and let the
  sandbox outlive the client, as branches do.
- One sleeping process per sandbox is the cost. It is bounded and idle.

## Not established

- Whether the joined process is reaped correctly when it exits while the holder
  is a `sleep`. During the probe the joined process appeared with PPID 0 inside
  the sandbox, so bwrap's reaper does not own it. Zombie accumulation with a
  long-lived holder was not measured.
- Whether `setns` behaves identically when litterbox is not the same uid as the
  sandbox process, e.g. a root-owned daemon.
- cgroup freeze of a holder whose members were reparented into the namespace:
  the freeze target is the holder's scope, which the joined processes do not
  belong to. This needs the scope to own the whole tree, or the joined process
  must join the cgroup as Flatpak's `--join-cgroup` does. Untested.
