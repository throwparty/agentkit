# 🎛️ Configuration

Litterbox configuration is split by who owns the decision:

- **The person running the code** owns the sandboxing mechanism: which backend, its
  settings, and where forwarded ports bind. That lives in the untracked local
  override and is never committed.
- **The project** owns what it needs: its provisioning steps, the ports it expects,
  and how snapshots are stored. That lives in `.agentkit/litterbox/config.toml`.

The committed project file may not select or configure a backend. If it tries,
Litterbox says so and ignores the setting; the sandbox runs on your machine, so
the choice is yours.

## Where the files live

| Scope           | Path                                                                         |
| --------------- | ---------------------------------------------------------------------------- |
| Project         | `.agentkit/litterbox/config.toml` in the repository                          |
| Local override  | `.agentkit/litterbox/config.local.toml` in the repository, project keys only |
| User config     | `~/.config/agentkit/litterbox/config.toml`, machine-owned                   |

Merge order is defaults, then the user config, then the project, then the local
project override. The repository-local file may not carry machine settings or
setup consent; those live in the user config outside the checkout.

## User configuration

```toml
# The sandboxing mechanism. Omit to use the default.
backend = "docker"

# Allow a repository's command steps to run. Off by default: cloning a
# repository must not be enough to execute its shell command on your machine.
allow-project-setup = false

# Or allow specific projects by their namespace: the project slug that
# `litterbox list` prints, including its suffix.
allowed-projects = ["my-project-1a2b3c4d"]

# Accept a degraded mechanism, where a capability falls back to something
# weaker, instead of refusing to start.
accept-degraded = false

# Where forwarded ports bind on the host. Loopback unless you say otherwise,
# and only ever set here.
[forwarding]
bind = "127.0.0.1"

# A section per backend, in that backend's own vocabulary.
[backends.docker]
image = "ubuntu:latest"
# Memory ceiling per sandbox, in MiB. At least 6. Defaults to 4096.
memory-mb = 4096
# CPU cores per sandbox. At least 1. Defaults to 2.
cpus = 2
# Maximum tasks or processes per sandbox. At least 1. Defaults to 512.
pids-limit = 512
# Extra Linux capabilities to grant, such as CHOWN or SETUID. Empty by default;
# every other capability is dropped.
cap-add = []
```

Prefer pinning the image by digest (`image = "ubuntu@sha256:..."`): a tag can
change under you, and the image is the sandbox's confinement boundary.

Every backend owns its section: Docker accepts `image`, `memory-mb`, `cpus`,
`pids-limit` and `cap-add`, and a key Docker does not define is rejected by name
rather than ignored. Granting a capability widens what code in the sandbox can
do; add only the ones an image genuinely needs.
`litterbox backends` reports what this machine can run, marks the selected
backend, and explains anything that will not start.

## Project configuration

```toml
[project]
slug = "my-project"
backends = ["docker"]

[[provision]]
identity = "setup"
kind = "command"
run = "echo 'Setup complete'"

[backends.docker]
provision = ["setup"]

[[ports]]
name = "web"
target = 8080

[git]
snapshot-mode = "direct"
```

- `project.slug` identifies the project. It must already be a valid slug; a value
  the rules would change is refused rather than silently rewritten.
- `project.backends` names the backends the project's provisioning supports. It is
  required when `[[provision]]` defines a step. The local override may replace it;
  selecting a backend it does not list is refused with both names. An empty list
  with no steps means no restriction; with steps it must name at least one.
- `[[provision]]` defines a step once, by `identity`. `kind = "command"` runs `run`
  once, confined, with the workspace as its working directory, after the
  workspace is materialised, in the order the selected backend lists it. A
  command step's environment changes do not persist to later steps.
- `[backends.<name>].provision` is that backend's ordered sequence of step
  identities. The list order is the execution order. `provision` is the one
  project-owned key in a backend section; every other key there remains
  machine-owned and is ignored with a notice when the committed project file sets
  it.
- A project may define at most 32 provisioning steps and list at most 32
  identities in one backend's sequence.
- `setup-command` used to live under `[project]`. It is now a `command` step; the
  old key is rejected with a message naming the replacement.
- `ports` declares what the project expects forwarded. The project cannot decide
  where those ports bind or who may reach them.
- `git.snapshot-mode` is `"remote"` (the default) to keep snapshots in an isolated
  bare clone, or `"direct"` to keep them as branches in your working repository.

`[project] setup-command` is removed. A configuration that still sets it fails
to load with a message naming a `command` step and the per-backend list.

A command that exits non-zero fails create with its identity, exit code and up
to 4096 characters of output. Host logs record the exit code and length only;
the bounded output is returned to the caller so an agent can report it.

`litterbox doctor` reports whether this project can create a sandbox here: the
selected backend and its readiness, the supported backends, and each step in the
selected backend's order with its state and remedy. It does not create anything.
`--json` emits the same report for scripts and tests.

## Local project override

`.agentkit/litterbox/config.local.toml` takes the project file's project-owned
shape. A `[project]`, `[[ports]]` or `[git]` entry there overrides the committed
value; `[project] backends`, `[[provision]]` and
`[backends.<name>].provision` are replaced wholesale, and an empty list is a
deliberate removal rather than a fallback to the project. Keep it untracked: it
describes this checkout, not the machine.

Machine settings and setup consent are rejected here; they belong in
`~/.config/agentkit/litterbox/config.toml`. Litterbox refuses a local override
that is tracked by Git, reached through a symlink, or larger than a small
configuration file; cloning a repository must not be able to grant itself setup
consent or choose its own backend.

A provisioning identity starts with a lowercase letter and continues with
lowercase letters, digits, hyphens or underscores. The same rule applies in the
committed project file.
