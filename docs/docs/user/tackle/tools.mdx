# 🧰 Tools

## The tool registry

Tackle inventories every tool in a single registry, namespacing entries by their source:

- `agent.<actor>` allows invoking an actor as a subagent.
- `client.<surface>.<method>` allows direct access to the RPCs exposed by the connected ACP client. Where supported, this can provide [filesystem](https://agentclientprotocol.com/protocol/v1/file-system) and [terminal](https://agentclientprotocol.com/protocol/v1/terminals) access.
- `mcp.<server>.<tool>` exposes tools from connected MCP servers. Note that ACP clients [can also advertise MCP server comfigurations](https://agentclientprotocol.com/protocol/v1/session-setup) the ACP server should connect to.
- `prompt.<name>` recalls reusable prompt.

Each registration carries visibility flags: _user-invokable_ (advertised to the client as a `/` command), _model-invokable_ (offered to the model as a tool), or both. The model always sees the namespaced name, so two servers can offer the same tool name without colliding. Namespacing makes cross-mechanism collisions impossible; within a namespace a project entry replaces a user entry of the same name, and a same-layer collision is a configuration error rather than a silent shadow.

## Direct invocation

Any MCP or client-capability tool can be invoked directly by the user, with no model request and no permission prompt:

```
/!mcp.litterbox.exec { "sandbox": "default", "command": "cargo test" }
```

The `!` prefix is advertised as a command so clients autocomplete it. It is recognised only on user-typed input and only as an exact first-token match, so pasted text is never hijacked. The result is reported as a tool call and stored in the turn. Oversized outputs are truncated at a fixed limit (16 KiB) with the original size recorded; the full content stays in the session store. `/!` on a prompt or agent invokable fails with a precise error — direct invocation reaches MCP and client-capability tools only.

## Adding MCP servers

Servers are defined in [the configuration](reference/config) as endpoints. They can be defined either globally (`config.toml`), or per-project (`.agentkit/tackle/config.toml`). Entries defined in the project are merged with the global ones, and project entry with the same name replaces the global entry wholesale.

A local server is spawned over stdio using an explicit `command`, `args`, and `env`:

```toml
[mcp_servers.litterbox]
transport = "stdio"
command = "litterbox"
args = ["mcp"]
env = { RUST_LOG = "info" }
```

A remote server is reached over streamable HTTP by `url`:

```toml
[mcp_servers.remote]
transport = "http"
url = "https://example.com/mcp"
```

### Spawn hygiene

stdio servers are started with an explicit argv and without a shell. Tackle's own environment is **not** forwarded, including `PATH`; if a server needs variables like `PATH` at runtime, set them explicitly in `env`.

### Trust

:::info

You can read more about our security posture in [the security model](security).

:::

Since `mcp_servers` are programs, any provided by projects require consent, granted for a specific configuration of each entry. Any change to an entry re-prompts.

## Wiring up credentials

Most servers need a secret such as an API token, or a personal access token. Never put it in the configuration. Instead set either an argument or an environment value to a credential marker and let Tackle resolve it at spawn:

```toml
[mcp_servers.github.env]
GITHUB_PERSONAL_ACCESS_TOKEN = "{cred:github}"
```

A `{cred:<identity>}` marker must be the **entire** value — `Bearer {cred:github}` is rejected. At spawn time Tackle will look up the value via your [credential helper](../utilities/credentials). Store the secret one time with [`tackle auth`](./reference/cli#auth):

```bash
tackle auth add github ghp_...
```

The helper is `credential_helper` from your user configuration, defaulting to `keychain`; under the hood Tackle runs `agentkit-credential-<helper> get tackle github` and reads `access_token` from the JSON output. `tackle auth status` lists each identity your MCP servers reference and whether it resolves.

Resolution happens when the server spawns, never at config load, so secrets never enter the configuration. A failed lookup fails that server's connection rather than the whole session; the reason appears in the first-turn status and in `/mcp status`.

## Calling tools

The model sees each connected tool as an invokable named `mcp.<server>.<tool>` and calls it like any other tool. You can also invoke one directly, with no model request and no permission prompt:

```
/!mcp.litterbox.exec { "sandbox": "default", "command": "cargo test" }
```

Oversized results are truncated at a fixed limit with the original size recorded; the full content is what the server sent and is kept in the session store.

## Managing servers at runtime

Every declared server is connected at session start and reported connected or failed, with a reason, in the first turn. Connection attempts are asynchronous with a per-server timeout to prevent failed servers holding up sessions.

Availability can be toggled at any point during a session with the `/mcp` command:

- `/mcp status [server]` reports each server's state.
- `/mcp disable <server>` closes the connection and drop the server's tools.
- `/mcp enable <server>` enables a disabled server.

## Client-capability tools

When the client advertises them, the editor's own file-system and terminal surface is reflected to the model as `client.*` tools — `client.fs.read_text_file`, `client.fs.write_text_file`, and the `client.terminal.*` family (`create`, `output`, `wait_for_exit`, `kill`, `release`). They execute against the connected client rather than an MCP server, and take the same permission pipeline as any other tool.

Toggle the categories for the connection with `/editor`:

```
/editor fs false
/editor terminal true
```

`[client_tools]` in user configuration seeds the toggles at startup; a category the client did not advertise is never exposed regardless. As with MCP tools, you can invoke a client tool directly:

```
/!client.fs.read_text_file { "path": "/abs/path/file.rs" }
```

## Checking it works

Start a session and read the first-turn report; `/mcp status` lists the same state. `remote: connected` (or a named failure reason) tells you the server was reached. A tool that fails a credential lookup shows up as `failed` with the helper's error.
