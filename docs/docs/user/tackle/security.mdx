# 🛡️ Security model

Tackle's security posture is to **fail-closed**:

- Allowing a tool invocation is never a default.
- Every extension point is bounded.

:::info

We believe that the harness is responsible for mediating the admission of data into the model's context window and the model's requests for access to resources. The harness and its configuration should not be configured by the model without the user's expess consent, and it therefore belongs outside of any compute sandbox.

:::

## Projects are untrusted

A cloned repository is untrusted input, but the sandbox is the consent boundary: launching Tackle in a repository already admits that repository's content to the sandbox. Context-bearing project configuration therefore loads without a prompt.

- Definitions — personas, actors, and prompts — are repository-resident, including any package resources. Their bodies and resources are context the model may already read, not host execution.
- Bounded Rhai project scripts load because the engine limits are the consent. See [Scripts are bounded](#scripts-are-bounded).

Unbounded host execution is denied at project scope:

- `mcp_servers` and `client_tools` declared by a project are ignored.
- `endpoints` and `credential_helper` are rejected outright.
- The same entries are honoured only from user configuration outside the repository.

There is no launch-time consent prompt. Configuration and definitions load once at process start without hot reload, so a change is picked up on the next run.

## Spawn hygiene

stdio MCP servers are started with an explicit argv or shell, with only the named environment variables accessible. Tackle's own environment, `PATH` included, is **never** forwarded.

## Credentials

Secrets never enter configuration and never enter model context. An environment value that is exactly `{cred:<identity>}` is resolved through the credential helper **at spawn**, not at load, so the secret exists only in the spawned process's environment. A marker that is not the whole value passes through literally; a failed lookup fails that server's connection rather than the session.

Logs redact credentials and tool arguments, and telemetry redacts sensitive payloads at the type level.

## Grants

The permission grant store is in-memory only. A grant never touches disk, does not survive process exit, and does not survive a resume after restart. See [Permissions](./permissions).

## Scripts are bounded

Script engines enforce operation, call-depth, expression-depth, collection-size, and time limits, cap script size, forbid module imports, and start fresh per invocation. Scripts cannot invoke tools and cannot read or write the grant store. A policy script that fails fails closed to ask.

## Permission assessment is in-core

The permission pipeline (including grants, policy scripts, and the fixed ask fallback) lives in the harness, deliberately **outside** any sandboxed development environment. An agent with shell access inside a sandbox cannot rewrite the access control that governs it.

Sandboxing itself is not tackle's job. Where you need real containment, run the agent inside a sandbox and reach tackle's tools from there — that is [Litterbox](https://github.com/throwparty/agentkit)'s role, and tackle reaches it only over MCP.

## Bounded inputs

Tool results are truncated at a fixed limit (16 KiB) with the original size recorded, bounding what a single server response can put in front of the model. The full content remains in the session store.
