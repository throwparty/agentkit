# 🧰 Setting up your tools

Tackle reaches tools through [MCP](https://modelcontextprotocol.io). Every tool a session can call comes from an MCP server, and every server's tools are namespaced `mcp.<server>.<tool>` so two servers can offer the same tool name without colliding.

## Where servers come from

A session's tool pool is assembled from two sources:

1. **Tackle's own configuration** — the `mcp_servers` entries described below.
2. **The ACP client** — a harness such as [Zed](./clients/zed) forwards the MCP servers from its own settings over ACP.

Both sets are available for the connection. This page covers the servers you declare to Tackle directly.

## Declaring servers

Servers live in the same [configuration layers](./setting-up-your-providers#where-configuration-lives) as endpoints: the user layer (`config.toml`), overlaid by the project layer (`.agentkit/tackle/config.toml`). A project entry with the same name replaces the user entry wholesale.

A local server is spawned over stdio — an explicit `command`, `args`, and environment:

```toml
[mcp_servers.litterbox]
transport = "stdio"
command = "litterbox"
args = ["mcp"]
env = { RUST_LOG = "info" }
```

A remote server is reached over streamable HTTP by URL:

```toml
[mcp_servers.remote]
transport = "http"
url = "https://example.com/mcp"
```

### Spawn hygiene

Stdio servers are started with an explicit argv — no shell, so nothing in `args` is interpreted — and with only the environment entries you name. Tackle's own environment is **not** forwarded, including `PATH`; if a server needs variables like `PATH` at runtime, set them explicitly in `env`.

### Trust

`mcp_servers` entries execute programs, so a project layer's entries are trust-gated: the first session in a project prompts for consent, keyed on a hash of each entry. Any change to an entry re-prompts, and unapproved entries are dropped before the merge. Endpoints and the credential helper are user-layer only — a project cannot set them.

## Wiring up credentials

Most servers need a secret — an API token, a personal access token. Never put it in the configuration. Instead, set an env value to a credential marker and let Tackle resolve it at spawn:

```toml
[mcp_servers.github.env]
GITHUB_PERSONAL_ACCESS_TOKEN = "{cred:github}"
```

A `{cred:<identity>}` marker must be the **entire** value — `Bearer {cred:github}` is rejected — and it resolves through your [credential helper](../utilities/credentials). Store the secret one time with [`tackle auth`](./reference/cli#auth):

```bash
tackle auth add github ghp_...
```

The helper is `credential_helper` from your user configuration, defaulting to `keychain`; under the hood Tackle runs `agentkit-credential-<helper> get tackle github` and reads `access_token` from the JSON output. `tackle auth status` lists each identity your MCP servers reference and whether it resolves.

Resolution happens when the server spawns, never at config load, so secrets never enter the configuration. A failed lookup fails that server's connection rather than the whole session; the reason appears in the first-turn status and in `/mcp status`.

## Managing servers at runtime

Every declared server is connected at session start and reported — connected or failed, with a reason — in the first turn. Connection attempts are asynchronous with a per-server timeout, so one dead server never holds up a session.

Availability is tunable for the life of the connection with the `/mcp` command:

- `/mcp status [server]` — report each server's enable and connection state.
- `/mcp disable <server>` — close the connection and drop the server's tools.
- `/mcp enable <server>` — reconnect a disabled server.

## Calling tools

The model sees each connected tool as an invokable named `mcp.<server>.<tool>` and calls it like any other tool. You can also invoke one directly, with no model request and no permission prompt:

```
/!mcp.litterbox.exec { "sandbox": "default", "command": "cargo test" }
```

Oversized results are truncated at a fixed limit with the original size recorded; the full content is what the server sent and is kept in the session store.

## Checking it works

Start a session and read the first-turn report; `/mcp status` lists the same state. `remote: connected` (or a named failure reason) tells you the server was reached. A tool that fails a credential lookup shows up as `failed` with the helper's error.
