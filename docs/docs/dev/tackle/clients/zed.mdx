# Zed

[Zed](https://zed.dev/) tends to lead in ACP client development, so it's a good place to validate features. This page records what it advertises today, and how to build it with ACP v2 support. It reflects Zed `main` as of 2026-10-23.

## Subagent sessions

Zed does not advertise the `subagents` client capability over ACP v1. Its `initialize` request is built in `crates/agent_servers/src/acp/v1.rs` by `client_capabilities_for_agent`, which sets `fs`, `terminal`, `auth`, session config options, compaction, notices, and elicitation, and never `subagents`.

Zed `main` has landed the client side of the [Subagent Sessions RFD](https://agentclientprotocol.com/rfds/subagents). It carries an `accepts_subagent_updates` flag read from `client_capabilities.subagents.is_some()`, and `apply_subagent_update` registers a child thread under its parent when an update arrives. The capability is still not advertised. A test named `client_capabilities_do_not_advertise_subagents` asserts that it is not, on the grounds that v1 subagent support is offered only behind the `acp-beta` flag.

The practical consequence is that a v1 agent must not send `subagent_update` to Zed. Such an update is dropped, with a log line reading "Zed did not advertise the subagents capability".

## How Zed models a subagent

Zed represents a subagent as its own `AcpThread`, created when the parent's `subagent_update` arrives (`crates/agent_servers/src/acp.rs`, `apply_subagent_update`). The child's notifications are applied to the child's thread and never reach the parent thread. That is the client-side form of the two-plane split a harness has to produce on the wire.

The association the parent holds (`crates/acp_thread/src/subagents.rs`, `SubagentAssociation`) carries only the parent's `title`, `description`, and whether `cancel` is permitted. It deliberately does not carry work state: `state` is the child's activity, and it lives on the child's own thread.

For v1, the parent-carried `state` snapshot is converted to the v2 `StateUpdate` shape through JSON, so unknown states and stop reasons survive the trip rather than being dropped. v1 `_meta` on the association is discarded, because v2 patches association metadata by top-level key instead.

## Cost and usage

Each thread stores its own usage. `AcpThread` holds `token_usage` and `cost` (`crates/acp_thread/src/acp_thread.rs:3932-3933`), both filled from that session's own `usage_update`. A subagent is an agent-owned thread of its own (`agent_owned`, line 3957) that the parent holds in a `subagents` map, and the client aggregates nothing from it. The subagent card in the parent thread shows a label, a status, an error, and a stop control, and no cost (`crates/agent_ui/src/conversation_view/subagent_card.rs`).

So the client never adds a parent's cost to a child's. The RFD's rules match this: cost is optional, a parent's reported cost may include child work, a child's may overlap, and clients must not sum. There is no cost-scope field and no accounting negotiation, so a harness cannot express an exclusive breakdown even if it wanted to. A harness that wants the parent's figure to cover its children has to report it that way itself, because nothing downstream will do it.

An idle state snapshot carries its own `usage` with input and output tokens, which `update_session_state` folds into the thread's token usage (lines 4569-4587). The child's foreground state is unconfirmed until the agent reports one, which is why `agent_owned` marks the activity unconfirmed (line 3959).

## The `acp-beta` flag

`acp-beta` is a Zed feature flag (`crates/feature_flags/src/flags.rs`). It is a plain presence flag that overrides nothing, so `enabled_for_staff()` keeps its default of true and `enabled_for_all()` is false.

In current `main` the flag selects the ACP v2 connection, falling back to v1 when negotiation fails. Subagents are part of the v2 baseline, so a v2 connection needs no capability for them.

## Feature flags

`FeatureFlagStore::try_flag_value()` resolves a flag in this order:

1. `enabled_for_all()`, which wins outright and is not set here.
2. A settings override, but only when `overrides_enabled()` is true.
3. The staff or debug-build default.
4. A server-delivered flag.

So the ways to turn `acp-beta` on are:

- **Staff** get it on by default, because `enabled_for_staff()` defaults to true.
- **Debug builds** get it on by default, because `cfg!(debug_assertions)` is treated as staff.
- **A settings override** sets `"feature_flags": { "acp-beta": "on" }` in `settings.json`. It is honored only when `overrides_enabled()` is true, which is `(debug build || staff) && !ZED_DISABLE_STAFF`. The settings UI writes this key through `FeatureFlagStore::set_override`.
- **Zed's server** can enable it per user by announcing the flag (`update_server_flags`). This is the only route for a non-staff release user, since overrides are a staff-only affordance.
- **`ZED_DISABLE_STAFF=1`** forces non-staff treatment, which is how the off state is tested.

## Checking a build

To confirm the behaviour for a given Zed build, look for `subagents` in `crates/agent_servers/src/acp/`. If `client_capabilities_for_agent` does not set it, the client will not accept v1 `subagent_update` notifications, and nested sessions fall back to parent representation.
